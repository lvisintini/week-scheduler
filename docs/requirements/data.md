# Persistence and data

- **R-DATA-01** **[U]** **Workspaces:** several named, fully independent data sets (schedules, people, activity types, events, rhythms, phases) live in memory at once; the sidebar has a **workspace switcher** under the title (menu: switch — each workspace with its colour and description, R-DATA-10 —, *Workspaces…* (R-DATA-10), *New workspace…*, *Rename current…*, *Duplicate current*, *Delete current…*, *Weeks in the cycle…* (R-CYC-01); • marks unsaved ones; the last workspace can't be deleted). `S` always points to the current workspace's data; `WS=[{id,name,data,lb,lf,undo,redo}]`, `curId`; `syncWs()` writes the live `S`/history back into the record before switching/saving; **undo/redo history, selection and dirty state are per workspace**. A *new* workspace starts from `defaultData()` (Routine schedule + default activity types + Normal rhythm; a one-week cycle); *Duplicate* copies the data and counts as unsaved. **Rejected [U]** (proposed as workspace follow-ups and turned down; not to be proposed again): statistics across workspaces, and showing another workspace in the background of the grid.
- **R-DATA-02** **[U]** **Save…** asks the target (browser memory / JSON file — encrypted by default, unencrypted on request (R-SHARE-07) / password-protected shareable link). **Files and links always hold exactly one workspace (the current one) [U]**; only **browser memory** asks, when there is more than one workspace, **which to save: only the current one or all** (browser memory can be protected with a passphrase, R-DATA-11). Browser memory (`localStorage` key `weekly-schedules-workspaces`, `{version:1,current,workspaces:[{id,name,…data}]}`): *current only* updates/inserts just that workspace's entry (other stored entries stay as last saved); *all* rewrites the whole store (deleted workspaces disappear). The (decrypted) content of a file/link is one workspace record `{version,id,name,schedules,people,types,events,rhythms,phases,phaseOpacity,cycle?}`.
- **R-DATA-03** **[U]** The app **auto-loads all workspaces from browser memory** at startup. **Load → Browser memory** reverts the *current* workspace to its saved copy (undoable). **Load → JSON file** and **opening a shareable link** never overwrite anything silently: both go through one **import dialog** for the single workspace they contain, with exactly three options: **Import as a new workspace** (default; name made unique; keeps the file's id when free), **Insert into the current workspace** (its schedules, people, rhythms and phases arrive as *new* items with new ids; name clashes get "(2)"; inserted rhythms are hidden unless none was visible) or **Replace an existing workspace** — a single option that opens a picker listing *all* workspaces (best candidates first) with flags for the *active* one, the one with the *same id* and the ones with the *same name*, followed by a **confirmation naming the workspace that will be replaced**. There is deliberately no separate "replace current" or "replace matching" option. After importing or replacing, the app switches to that workspace. **Nothing is ever merged** (no occurrence/event merging, no conflict resolution) **[U]**. Inserting events whose weeks lie beyond the current cycle asks first (R-CYC-13). Replace/insert are undoable in the affected workspace; imported-from-file workspaces count as saved (file), imported-from-link ones as unsaved. A first-time visitor with no browser memory and an untouched default workspace opening a link adopts it directly.
- **R-DATA-04** **[U]** **Copy/move between workspaces:** schedule and rhythm rows have *Copy or move to workspace…*: a **schedule** goes with all its events (attached only to the new schedule); a **rhythm** goes with all its phases; **individual phases cannot be copied or moved to another workspace [U] — only whole rhythms (with their phases)**; the Copy dialog for a phase only offers rhythms of the current workspace. For schedules, every person referenced by the events (responsible per repetition, involved) is listed in a **people mapping dialog**: *create that person in the target*, *use an existing target person* (default: same name, case-insensitive; otherwise create), or *leave blank* (no responsible person / not involved). Copies get unique names in the target; weeks beyond the target's cycle ask first (R-CYC-13); both workspaces get an undo step; *move* removes the item from the source afterwards (schedule: events only in it are deleted; phase/rhythm likewise). **A single event** **[U]**: with more than one workspace, its Copy dialog (the event dialog's *Copy…*, right-click, touch Copy) first asks for the **Workspace** (*Home (this workspace)* first); another workspace lists its own schedules, and the buttons are **Copy** and **Move** (*Move* only to another workspace, tooltip). It goes through the same steps as a schedule (`carryEvents`, shared with the schedule transfer): the people mapping dialog, activity types by name, the cycle question, an undo step in the target, and for *Move* one here. **People** **[U]**: a person's ⋯ menu has *Copy to workspace…* (`openPeopleCopy`): the target workspace and a tick list of everyone (this person ticked; external people marked), copying name, colour and the external mark; a name the target already has (case-insensitive) is shown *already there* and can't be ticked; one undo step in the target. Copy only (moving a person would be deleting them here).
- **R-DATA-05** **[U]** **Clear memory** (confirmation) deletes the whole store (all workspaces) **and restarts the app** with one default workspace. **Restart** discards unsaved changes in all workspaces and reloads browser memory. `beforeunload` warns when *any* workspace has unsaved changes; a workspace is dirty when its data differs from both its last browser save and its last file save; the sidebar title shows • when any is dirty.
- **R-DATA-06** **[U]** **View settings are per browser, not in the save file** (`prefs`, key `weekly-schedules-prefs`): `showEarly`, `clock12`, `hideWeekend`, `theme` (`auto`|`light`|`dark`), `rowH`, `colW`, `fitW`, `fitH`, `rowHP`, `fitHP`, `colWP`, `fitWP` (a phone's own row height and width), `txt` (R-GRID-07); `live` (R-GRID-12), sidebar width (`w`) and `collapsed` (R-UI-01, R-UI-13), `hlNoType`, `colBy`, `lanesFix` (R-UI-11, R-EVT-23), `wsOrder` (the order of the workspace menu: workspace ids, R-DATA-10), `lvAnchor` (today's week per workspace: `{workspace id: 'YYYY-MM-DD'}`, the Monday of a week 1, R-CYC-05), section collapse flags (`secSch`, `secPpl`, `secTyp`, `secRh`, `secTools`, `secZoom`, and `secExt` for the External people sub-group, folded unless `false`); retired keys, never read again: `fillW` and `fit` (R-GRID-07), `side` and `sideFix` (R-EVT-10/13). The shown week of a cycle is never stored (R-CYC-04); today's week is stored only as `lvAnchor` (R-CYC-05). Data and view state are separated; *within* the file, `schedules[].visible/opacity`, `people[].visible`, `types[].visible`, `rhythms[].visible` and `phaseOpacity` are view state (saved, but ignored by `dataKey()` and preserved across undo).
- **Workspace data shape** (used inside the browser store, in files and in links):
```
schedules [{id,name,color,opacity,locked,visible}]
people    [{id,name,color,visible,external?}]   (external: true or absent)
types     [{id,name,color,icon,soft?,visible}]   (icon: a TICONS key; soft: true or absent; colour for statistics and for repetitions with col 't')
events    [{id,title,desc,color,type?,owner?,oncall?,nest?,bg?,away?,weeks?,turns?,schedules:[id],involved:[personId],slots:[{day,start,end,person,wk?,fo?,inv?,col?,flex?,fs?,fe?}]}]   (turns: true (always counts turns) / false (never) / absent (automatic), R-CYC-18; away: true or absent, never with bg, R-EVT-24; weeks: sorted week numbers of a pattern, absent = every week, R-CYC-02; wk: the repetition's week 1…cycle, on every repetition of a per-repetition event, never with weeks, R-CYC-03; owner: a person id or absent, R-EVT-20; fo: true when the day follows the owner (person = owner); inv: the day's own involved people, absent = the event's list, R-EVT-21; col: `'p'` (the performer's colour), `'t'` (the activity type's colour) or `#rrggbb`, absent = the event's colour, R-EVT-22; type: a type id or absent; oncall: true or absent; nest: true or absent, R-NST-01; bg: true or absent, R-EVT-19; flex: true or absent; fs/fe: flexible minutes after the start / before the end, > 0 or absent, never with flex)
rhythms   [{id,name,visible}]
phases    [{id,title,desc,color,weeks?,rhythms:[id],slots:[{day,start,end,wk?}]}]   (weeks / wk: as for events, R-CYC-16)
phaseOpacity 0.05–1 (default 0.3)
cycle     2–4 weeks, absent = 1 (R-CYC-01)
weekInfo  [{name?,desc?,color?}] one per week, trailing empty ones dropped, only with a cycle (R-CYC-17)
color     the workspace's colour, #rrggbb, absent = none (R-DATA-10)
desc      the workspace's description, ≤ 300 characters, absent = none (R-DATA-10)
```
**R-DATA-07** `day` 0 = Monday; times in minutes on a 15-min grid; event `start` 0–1425, `end` ≤ 2880; phase `end` ≤ 1440. `parseData()` is the single place that validates/sanitises input (clamps ranges, hex colours only, string length caps, drops events/phases without repetitions; normalises `cycle`, `weeks`, `wk`, `away` and `weekInfo` as R-CYC-03/14/17 and R-EVT-24 say). It works on the **current** format only; older formats are upgraded before it (R-DATA-08). Development formats from before the launch are not supported (no legacy keys or shapes). Callers assign `S` themselves.
- **R-DATA-08** **[U]** **Backwards compatibility from the launch on:** everything saved by any released version must keep loading with the same meaning. **One version number** for the data format, `FMT` (now **14**: version 1 was frozen at launch, 2 added `event.nest`, 3 added `event.bg`, 4 made strips come only from `event.bg`, 5 added `event.owner`, `slot.fo` and `slot.inv`, 6 added `slot.col` (R-EVT-22), 7 added the value `'t'` of `slot.col`, 8 added `types[].visible` (R-TYP-04), 9 added the cycle (`cycle`, `event.weeks`, `slot.wk`, R-CYC-14) and `event.away` (R-EVT-24), 10 added `weekInfo`, the weeks' names, descriptions and colours (R-CYC-17), 11 added the weeks of phases, `phase.weeks` and a phase's `slot.wk` (R-CYC-16), 12 added `event.turns`, whether an event counts turns (R-CYC-18), 13 added the workspace's `color` and `desc` (R-DATA-10), 14 added protected browser memory, `{version, sealed}` (R-DATA-11; a workspace record is unchanged); `MIG[1]`, `MIG[2]`, `MIG[5]`, `MIG[6]`, `MIG[7]`, `MIG[8]` `MIG[9]`, `MIG[10]`, `MIG[11]`, `MIG[12]` and `MIG[13]` change nothing because older data has none of the new marks; `MIG[3]` marks `bg` on every event whose repetitions are all led by external people with nobody involved or only people on call, i.e. the strips of the old rule — events that were partly strips become boxes; `MIG[4]` guesses an owner, R-EVT-20): the version of a workspace record in files and links, and of the browser store (whose entries carry no version of their own). **[U]** It goes up on **any** change to what is stored, even an added optional field, because an older app drops fields it doesn't know and would lose them on the next save. **Upgrading:** `migrate(record, version)` runs before `parseData` on every input (file, link, each workspace of the browser store at startup, *Load → Browser memory*): the steps `MIG[n]` (raw version-n JSON → n+1) run one after another, so `parseData` only ever sees the current format; steps are never deleted. A missing version counts as 1 (hand-written files), a numeric string is accepted, anything else (0, negative, fractional, text) is *not a valid save file*. Old browser memory is upgraded in memory only and rewritten in the current format when the user saves (saving only the current workspace also upgrades the other stored entries). **Settings** (`prefs`) have no version (none = 1): a key never changes its meaning, and unknown or missing values fall back to the defaults; add a version only when one is needed. The fixed names (`weekly-schedules-workspaces`, `weekly-schedules-prefs`, `weekly-schedules-encrypted`, `#data=e1.`) never change. **[C✓] How to change the format:** raise `FMT`, add `MIG[FMT-1]`, update `tests/fixtures/household.js` (the sample household, in the current format, using every optional field, plus an `ADDED[FMT]` entry that removes the new fields again so older sample files are compared with `householdAt(v)`), run `node tests/fixtures/make.mjs` (writes `tests/fixtures/v<FMT>/` with the app's own save functions and refuses to overwrite a folder) and add the new key list to `SHAPES` in `tests/app/compat.test.js`. The settings sample (`prefsSample`) always differs from every *current* default; `prefsAt(v)` gives the sample a folder was written with (folders up to 5 hold the retired `fillW`/`fit`, up to 8 the retired `side`/`sideFix`; settings added later — `PREFS_AFTER` — are absent there). **Sample files of every published version** (`tests/fixtures/v<N>/`: readable file, encrypted file, link — password in `household.js` —, browser store with two workspaces, from version 14 also that store protected with the same password (`store-protected.json`, R-DATA-11), settings) are **never edited or regenerated**; tests load each through the real screens and check the content. A **shape check** fails when the keys the app writes differ from the frozen list of the current version, so a format change without a new version number can't slip through.
- **R-DATA-09** **[U]** **Data from a newer version is refused, never half-read** (it only reaches an older app through a stale cached page or an old copy kept on disk): a file or link whose workspace version is above `FMT`, an encrypted file whose container `version` is above 1, a blob whose layout byte or compression flag is above 1, or a link prefix `e2.` and up gives the message *made with a newer version… Reload the page (or update your copy of the app)* — before the password is asked whenever the version is visible from outside — and changes nothing. **Browser memory written by a newer version** (plain, or protected with a passphrase, R-DATA-11: its outer `version` is checked without decrypting) is neither loaded nor overwritten: at startup an alert explains it and the app starts with a default workspace; saving to browser memory (current or all, also when another tab wrote the newer data later) and *Load → Browser memory* are refused with an explanation; *Restart* checks again; saving to a file still works; *Clear memory* (with its confirmation) deletes it, after which saving works again. A first-time visitor opening a link gets the import dialog instead of adopting it, since browser memory is not empty.
- **R-DATA-10** **[U]** **Workspace housekeeping:** a workspace may have a **colour** and a **description** (≤ 300 characters), stored in its data (`color`, `desc`; format 13, R-DATA-08): undoable, an unsaved change, saved in browser memory, files and links, kept by `parseData` only as a hex colour and a trimmed text; *Leave out personal details* drops the description and keeps the colour (R-SHARE-02) **[U]**, chosen over keeping them per browser. **Workspaces…** in the workspace menu opens a dialog (full screen on a phone) with a row per workspace: a **grip** (drag, or the arrow keys) for the **order of the menu**, a **colour swatch** with ✕, **Name** and **Description**; one **Apply** changes everything (an undo step in each workspace whose colour or description changed; names as with *Rename current…*). **The order is this browser's** (`prefs.wsOrder`, workspace ids; R-DATA-06) **[C✓]**, since another device has its own workspaces: applied when browser memory is loaded (`orderWs`), unknown workspaces after the known ones, not undoable and not an unsaved change. **Where it shows:** the workspace button gets a left edge in the colour and the description in its tooltip; the menu shows each workspace's colour chip and its description under its name; printouts show the chip before the workspace's name (R-PRN-02). The grip is the dialogs' shared `rowGrip`, also used by *Weeks in the cycle…* (R-CYC-20).
- **R-DATA-11** **[U]** **A passphrase for browser memory** (*frase de contraseña*): browser memory can be **protected**, so that what this browser saves is encrypted and someone with access to the browser profile or the disk (another user of a shared computer, devtools on a closed page, a copy of the disk) cannot read it. **One passphrase for all of browser memory [U]** (every workspace together; files and links keep their own passwords, R-SHARE-01). **Stored** under the same key as a plain store, as `{version, sealed}`: `sealed` is the base64url blob of the plain store `{version,current,workspaces}` in the file/link layout (deflate, PBKDF2-SHA256 600,000 → AES-256-GCM, R-SHARE-04), so it is still only two `localStorage` keys (R-SEC-04); `prefs` stays plain (view settings and workspace ids only) **[C✓]**. The outer `version` is always the app's `FMT` (format 14, R-DATA-08), so an older cached page refuses it as newer (R-DATA-09) instead of saving over it **[C✓]**. **The key** is derived once (when the page opens it, or when protection is turned on), is non-extractable and lives only in the page (`memKey`); every save reuses it with a new IV, so saving stays instant **[C✓]**. **Opening the page [U]:** a protected store first shows *Browser memory is protected* over an empty grid (passphrase, *Show passphrase*, **Open**); a wrong passphrase says so and lets you retry; the dialog cannot be dismissed (Escape does nothing; if the browser closes it anyway, it comes back). Today's week, Live View and a shared link (whose password is asked after the passphrase) wait for it (`afterStore`). **Without the passphrase [U]** the only way on is *Forgot it? Erase browser memory…*, after a confirmation saying it cannot be recovered; the app then starts with an empty workspace. A forgotten passphrase cannot be recovered **[U]**. **Stays open until the page closes [U]:** reloading asks again; there is **no idle timeout** (a Live View wall screen keeps showing) **[U]**. **Settings → Data [U]:** *Passphrase…* (Protect browser memory: the passphrase twice, *Show passphrase*, *Suggest one* (`genPassword`), a warning to keep an encrypted file as a backup); **at least 8 characters**, the two must match, surrounding spaces ignored **[U]**. Protecting with nothing saved writes an empty protected store, so the protection is kept. While protected the tab says so and offers *Change passphrase…* (the current passphrase, then the new one twice, so a passer-by at an open page cannot change it), **Lock now** (asks first when there are unsaved changes, then drops the key and the data from the page and shows the unlock dialog) and *Remove passphrase…* (asks for the passphrase, then stores browser memory readable again) **[C✓]**. Buttons rather than a switch, like Restart and Clear memory in the same tab **[C✓]**. **While open**, saving (current or all), *Load → Browser memory* and *Restart* use the open key and never ask again; the Save and Load dialogs read *Browser memory (protected)*; *Clear memory* also removes the protection. **Another tab** that turned the protection on, off or changed the passphrase since this page opened browser memory: saving to or loading from browser memory here is refused with *…changed in another tab or window… Reload the page*, and nothing is overwritten **[C✓]**. **What it does not protect** (help tip, `help21`): anyone using the open page, and malware on the device; it protects saved data **[C✓]**.
