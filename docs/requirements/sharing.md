# Sharing: protected files and links

- **R-SHARE-01** **[U]** **Protected links and files** (reason: the data may describe vulnerable people such as children or the elderly): **links always require a password — there is no unencrypted link [U]**; JSON files are encrypted by default and only unencrypted when the user explicitly chooses so (R-SHARE-07). Save… → *JSON file* / *Shareable link* open one dialog with the options and the password field. Without `crypto.subtle` (old browsers/insecure contexts) links and opening encrypted files are refused with an explanation — never a plain fallback; the file dialog then only offers *Unencrypted* (with its warning, still a deliberate click on Save file).
- **R-SHARE-02** **[U]** *Leave out personal details* checkbox (unticked by default): people become "Person 1", "Person 2"… and event/phase descriptions are removed — `anonymised()`; week descriptions are removed too (R-CYC-17); titles, schedule/rhythm/workspace names, the cycle, week patterns and week names are kept and the dialog says so; an anonymised export is **not** treated as a backup, i.e. it doesn't mark the workspace as saved to file.
- **R-SHARE-03** **[C✓]** The password field is pre-filled with a generated password (**25 random characters in 5 groups of 5**, unambiguous alphabet without 0/O/1/l/I, unbiased `crypto.getRandomValues`, ~145 bits) that can be regenerated or replaced; any password must be **at least 20 characters** (trimmed) **[U]** (**Rejected:** a shorter minimum). The dialog tells the user to give the password to the other person by a *different route* than the link/file; the result dialog has *Copy* buttons for link and password.
- **R-SHARE-04** **[C✓]** Crypto (Web Crypto, no libraries): JSON → raw-deflate (if `CompressionStream` exists; flagged inside) → **AES-256-GCM** with a key from **PBKDF2-SHA256, 600,000 iterations**, random 16-byte salt and 12-byte IV per export; blob = `[1][iterations u32][salt][iv][ciphertext+tag]` with the header authenticated; decryption refuses iteration counts outside 100k–2M (crafted-file DoS), wrong passwords and altered data fail cleanly, and the decompressed size is capped at 2 MB (a decompression bomb gets the *too many items* message in the password dialog, not *not a valid save file*).
- **R-SHARE-05** **[C✓]** **Links:** `<app url>#data=e1.<base64url blob>` — in the URL fragment, which is never sent to web servers and not fetched by link previews; the result dialog shows the link and the password, the length (warning above 8,000 characters); the app is always served (opening it from disk is not supported **[U]**), so there is no local-file note. **Opening:** `askPassword` (masked, show toggle, retry on wrong password); links are only understood in the `e1.` form (`e2.` and up: R-DATA-09) and re-checked on `hashchange`; the fragment is removed from the address bar after success or cancel. After decryption the content goes through the normal import dialog (or is adopted by a pristine first-time visitor). Invalid/too-large links show a toast and change nothing; a payload too short to be an encrypted blob (empty, truncated, or with an impossible layout byte) is refused with that toast at once, without asking for a password (`sealedOk`).
- **R-SHARE-06** **[C✓]** **Files:** `{format:'weekly-schedules-encrypted',version:1,data:<base64url blob>}` named `weekly-schedules-<date>-encrypted.json` (`<date>` = today's local date, `YYYY-MM-DD`, in the names of every downloaded file: `fileDay`) (the name deliberately doesn't reveal the workspace). Opening a file asks for the password (retry on mistakes), except when its data is too short to be an encrypted blob or has an impossible layout byte: that is *not a valid save file* at once; encrypted files and *plain* hand-written JSON files can both be imported (`weekly-schedules-encrypted` container detected by `format`). The dialog title is *Save JSON file*.
- **R-SHARE-07** **[U]** **Unencrypted JSON files (files only, never links [U]):** the JSON-file dialog has a switch **Encrypted (recommended)** (default, every time — the choice is never remembered) | **Unencrypted**. Unencrypted hides the password field and shows a warning box: anyone who gets the file can read everything, including plans of possibly vulnerable people (forwarded email, shared/cloud folder, lost USB stick, shared computer); use it as a private backup and prefer encryption or *Leave out personal details* when sending it. The file is the readable workspace record (the same shape plain imports accept) named `weekly-schedules-<date>.json` (no `-encrypted`); it counts as a backup (marks the workspace saved to file) unless anonymised; it opens without a password through the import dialog. `saveFile(null, anon)` = unencrypted.
- **R-SHARE-08** **[U]** **Sharing only part of a workspace** (for example only the children's schedule, or only their activities, for the grandparents): the *JSON file* and *Shareable link* dialogs have **What to include**: **Everything** (default) or **Choose…**, which shows three tick lists: **Schedules** (all ticked at first; an event goes with the ticked schedules it belongs to and is left out when none is ticked), **Rhythms** (phases go with their rhythms) and **Only the activities of** (none ticked = everyone; ticked people keep only the **times they perform or are involved in** — the performer, the event's or the day's With list — so a rota keeps only their turns; ⓘ tooltip) **[U]**, chosen by the user over schedules and rhythms alone. A live summary says *12 of 40 events, 7 of 7 phases*; nothing left to share is refused with a message. The copy holds **only the people and activity types its events use**; the cycle and the week names travel as they are; *Leave out personal details* (R-SHARE-02) applies on top. **A partial copy gets a new id** **[C✓]** (its name stays), so an import never takes it for the whole workspace by id (R-DATA-03), and like an anonymised copy it is **not a backup** (the workspace is not marked as saved to file). `partOf(file, choice)` builds it; `shareOf` applies it and `anonymised` for both files and links.
- **R-SHARE-09** **[U]** **Calendar export** (*Archivo de calendario*): **Save… → Calendar file (export only)** **[U]**, a fourth button after *Shareable link*, downloads an iCalendar file (`weekly-schedules-<date>.ics`, `text/calendar`) for Google Calendar, Apple Calendar or Outlook. **A file, never a push** **[U]**: the app sends nothing anywhere and opens no windows (R-SEC-04), so a direct "add to Google" or a subscribed calendar (a URL the calendar re-reads, which would keep it in step) is ruled out; Google Calendar imports `.ics` files, so one export covers all three.
  - **Export only, one way** **[C✓]**: the button says *export only* and the dialog says that the file cannot be opened in the app again, that changes made in the calendar never come back, and that a JSON file or browser memory stays the backup; it is **never a backup** (the workspace stays unsaved, `lf` untouched).
  - **Periods that add up** **[U]**: every export has **From** (a date; by default **today** **[U]**, or the day after the last remembered Until when that is later) and an optional **Until** (a term, a month; empty = the events repeat forever). Each series starts on its first matching day on or after From, so earlier days are never added; Until before From, or no From, is refused with a message. Because **ids include From**, importing the same period again adds nothing in calendars that match ids, and a later period adds its own series and leaves the earlier ones as a record **[U]**. Rejected: Until required (tidy, but "my routine from now on" would need an arbitrary end), and replacing only (no history).
  - **The last export is remembered in this browser** **[U]**, per workspace (`prefs.icsLast`, R-DATA-06; view state, never in the data, files or undo): the dialog says *Last export from this browser: 21 Oct 2026 – 18 Dec 2026*; when that export had no Until it adds that it **never stops** and how to end it before importing a new period (in the calendar, on each series, delete "this and following events" from the new From date) or to replace the calendar; ⓘ: exports made on another device are not known here. *Delete* and *Clear memory* forget it, *Duplicate* does not copy it; a damaged value is ignored at load. This is the second date the app keeps (R-CYC-01).
  - **Dates** **[U]**: with a cycle of several weeks the week of each date comes from this browser's anchor (R-CYC-05), asked first (*Which week is it?*, *Continue*) when it is not known; the dialog says which week From is in (*The From date is in Week 2 · At Dad's*). **Floating local times** **[C✓]** (no time zone): 07:30 stays 07:30 across clock changes and when travelling. A time past midnight simply ends the next day (Sunday into Monday, the next week of the cycle, R-CYC-06).
  - **Series** **[U]**: days of one event that share start, end, performer, With list and timing become **one weekly series** (`RRULE:FREQ=WEEKLY;WKST=MO;BYDAY=MO,TU,WE,TH,FR`), so "all events" in the calendar changes those days together; other times are series of their own (a calendar series has one time). An every-week event repeats weekly; a week pattern or a time with its own week (R-CYC-02/03) is one series per week, `INTERVAL=` the cycle length. Rejected: one series per day.
  - **Ids** **[U]**: `UID:<event id>-w<week, 0 = every week>-<start>-<end>-<From>@weekly-schedules`, `-2`, `-3`… for series with the same times but other people: stable for the same data and From, unchanged when other days are added or removed, new for another From.
  - **What each kind becomes** **[U]**: normal and nested events are **busy** (`TRANSP:OPAQUE`) over their whole time, flexible start/end margins explained in the details; *Around these times* (R-EVT-12) and **Away** (R-EVT-24, titled *Away: …*) are **free** (`TRANSPARENT`); *In the background* (R-EVT-19) and rhythms and phases are **left out**. Rejected: everything as busy events; only the solid cores.
  - **People are text** **[U]**: the title carries the performer (*Cook dinner · Ana*, the plain title when nobody performs it); the details hold the description, *Owner:* when someone else performs it, *With:* or *On call:* and the week of the cycle; the activity type is the category. **No attendees and no organizer** **[C✓]**: calendars need email addresses (the app has none and collects none) and would offer to send invitations; every event belongs to whoever imports it.
  - **Reminders** **[U]**: *Reminder*: None (default, every time, never remembered), 5, 10, 15, 30 or 60 minutes before: a pop-up alarm (`VALARM ACTION:DISPLAY`) on **busy events only**. Apple Calendar and Outlook use it; whether Google's import keeps it is not documented, and email reminders cannot come from a file, so the steps say to set the new calendar's notifications there.
  - **Guidance** **[U]**: four short steps in the dialog: create a new calendar (removing it removes every exported event at once, while events in one's own calendar can only be deleted one series at a time), import the file into it, set its notifications there, and later either replace the calendar or export the next period (always with an Until if periods will be added). The ⓘ and help 22 give generic paths for Google, Apple and Outlook (kept generic so they stay true), sharing that calendar read-only from the calendar app or exporting each person's activities into a calendar of their own, one colour per calendar (per-event colours don't import reliably), that deleting one occurrence in the calendar is lost when it is replaced, and that changing the cycle, reordering its weeks or deleting events here means replacing the calendar.
  - **What to include** and **Leave out personal details** work as for files (R-SHARE-08, R-SHARE-02), with no Rhythms list and a summary of events only (*12 of 40 events*); nothing for a calendar is refused with a message. **Privacy** **[C✓]**: the file is not encrypted, and the warning adds that once imported the calendar provider (Google, Apple, Microsoft) keeps the plans on its servers. Not exported: per-repetition colours, icons, the cycle's structure.
  - Code: `js/ics.js` (`icsText(record, {from, until, rem, wk, now})`, pure; `openIcs`, `saveIcs`); the picker is `incPicker`, shared with files and links.
