# Security (threat assessment decisions)

Threat model: a static, client-only app (no server, accounts, network calls or third-party code); the data at stake is personal schedule information in the browser and in shared files/links. Decisions **[U]**:
- **R-SEC-01** **Content-Security-Policy** `<meta>` in the page (GitHub Pages sets no headers): `default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'none'; base-uri 'none'; form-action 'none'`. **[U]** **Scripts may only be the app's own files** (`js/*.js`, `script-src 'self'`; one module script, `js/main.js`, that imports the others by relative address, R-CODE-01): no inline `<script>`, no inline event handlers (`on…=`), no `javascript:` links, no `eval`. So even if an escaping bug (R-SEC-02) let a malicious shared file or link inject markup, the injected code would not run — it could otherwise navigate the page away with the decrypted data in the address (CSP does not block top-level navigation) or change the saved data. This was possible once opening from disk stopped being a requirement (`product.md`); the code moved out of `index.html` into `js/` and `app.css`, served as they are (no bundler, no build, no hash to keep in step). **Rejected:** keeping one file with the script's hash in the policy (a step after every code change) and a bundler (a build before every test and deploy) **[U]**. `'unsafe-inline'` stays for **styles only**: the code writes `style=""` attributes in HTML strings, and CSS cannot run code. `'self'` on GitHub Pages is the whole `lvisintini.github.io` origin, which is acceptable: injected markup cannot add a script that runs. Network access stays closed (`connect-src 'none'`, images only from the site itself — the pictures of How to use, `img/help/`, R-UI-17 — or as `data:`; `img-src 'self'` was added for them **[U]**: an injected image of the site can't run code or send anything away); `frame-ancestors` (clickjacking) can't be set from a meta tag on GitHub Pages — accepted, low impact. **Any new resource type (fonts, images from URLs, workers, network calls) needs a deliberate CSP change; check the browser console for "Refused to…" messages after edits.**
- **R-SEC-02** **Escaping rule:** every piece of user-controlled text that goes into `innerHTML`/`insertAdjacentHTML` must pass through `esc()` (escapes `& < > " '`); prefer `textContent`/DOM properties. Imported colours are reduced to `#rrggbb`, names/titles capped at 200 and descriptions at 5,000 characters (a week's name at 40 and its description at 300, R-CYC-17); names typed into the sidebar's rename fields (schedules, people, activity types, rhythms) are trimmed and capped at 200 too (an empty or all-space name keeps the old one).
- **R-SEC-03** **Import limits** (`LIM`, files and links only, never the browser store): 100 schedules, 500 people, 100 activity types, 5,000 events, 100 rhythms, 2,000 phases, 200 repetitions per event/phase (also with a cycle of weeks, R-CYC-14); links additionally capped at 2 MB when decompressed. Exceeding a limit rejects the import with a clear message.
- **R-SEC-04** **Nothing leaves the device** (except files the user downloads: the JSON export, the statistics CSV and the calendar file, R-SHARE-09, the only three `Blob`s): no `eval`, `new Function`, `document.write`, `fetch`/XHR/WebSocket/`sendBeacon`/`window.open`, no cookies, no third-party code; only the two documented `localStorage` keys are written (the workspaces key may hold browser memory protected with a passphrase, `{version, sealed}`, R-DATA-11; the key derived from it is non-extractable and lives only in the open page). **The one link out [U]:** Settings → About's link to the source code on GitHub (R-UI-15), an `<a target=_blank rel="noopener noreferrer">` built by the scripts: it is a navigation only the user's click starts, it opens in a new tab that gets no opener and no referrer, and it sends nothing from the app; the CSP needs no change for it. It is the only web address in the scripts besides the SVG namespaces, and `index.html` has none.
- **Link/file privacy:** links are always encrypted with a user-visible password, exported files too unless the user deliberately picks *Unencrypted* after a warning (see `sharing.md`); the data sits in the `#` fragment. Limits that remain: whoever has link *and* password can read and forward it (no revocation/expiry without a server), a short or reused password can be guessed offline (hence the generator and the 20-character minimum), the link length hints at the amount of data, imported/saved data is plaintext again in browser memory and in memory-only exports such as an anonymised copy's source, and a tampered hosted page could capture typed passwords (repo/hosting protection).
- **R-SEC-05** **Hosting advice (not code):** on GitHub Pages all sites of one account share the origin `name.github.io`, so other pages there can read this app's saved data → prefer a custom domain or a dedicated account/organisation; protect the repository (two-factor sign-in, protected main branch, HTTPS enforced) because whoever can change the code can read users' local data. Browser storage is unencrypted (shared computers: use Clear memory; keep JSON backups).
- **Automated checks:** see the Testing section of `CLAUDE.md` and `../testing.md` (`npm test`, `npm run test:e2e`). Re-run them after every change that touches HTML building, import or links.
