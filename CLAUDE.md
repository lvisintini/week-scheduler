## 1. Product
A single static `index.html` (HTML + CSS + vanilla JS, no libraries, no network requests) that must work when opened from disk or GitHub Pages. A weekly planner organised in **workspaces** (several independent named data sets in one browser), each with overlayable **schedules**, **events** with repetitions, **people**, and background **rhythms** made of **phases** (named parts of the day). English/Spanish UI. Repo files: `index.html`, `README.md`, `CLAUDE.md`.

## 2. Calendar grid
- **R-GRID-01** **[U]** Columns Monday→Sunday, left to right. Days are **not** attached to dates (it's a repeating week).
- **R-GRID-02** **[U]** Hourly rows from 05:00 to midnight by default; 00:00–05:00 hidden but can be shown (Settings → "Show early hours"). Events/phases in hidden hours are kept; they count in the "N hidden" badge (events only).
- **R-GRID-03** **[U]** **Saturday and Sunday: only the header cells have a different hue** (not the whole column). The hue covers just the header cell *between the day column's borders* — it must not extend into the phase-lip lane on the left, **except** the lane between Saturday and Sunday (both weekend headers), which takes the same hue so the two headers read as one band (class `wj`; the lane between Friday and Saturday stays neutral; the single-day print drops the join). Dark-mode variant exists (`--weh`).
- **R-GRID-04** **[U]** Settings: show/hide Saturday & Sunday columns; AM/PM clock; show/hide a red **now line** on the current weekday's column (updates every 30 s, default on, never printed).
- **R-GRID-05** **[U]** Midnight is always displayed as `00:00` (`12:00 AM` in AM/PM mode), never `24:00`.
- **R-GRID-06** **[C✓]** 48 px per hour, 15-minute snapping, hour lines, sticky day headers. Each day header shows an **agenda icon**; clicking the header opens that day's agenda **[U]**.
- **R-GRID-07** **[U]** **Zoom (grid scale only, never the text):** the sidebar's **Zoom section** (collapsible like the others, `secZoom`; moved out of Settings completely **[U]**; sliders have `aria-label`s and tooltips, checkbox explanations are tooltips) has a *row height* slider (px per hour, 24–120, default 48), a *column width* slider (px per day, 70–600, default 110) **[U]** with a **Fill the window width** checkbox (`fillW`, default on **[U]**): on = columns are *at least* the slider width and stretch over free space (never an empty strip right of Sunday); off = the width is **exact** (a narrower week leaves empty space on the right). Either way a week wider than the window scrolls sideways — that is how to make room for side-by-side lanes (R-EVT-10). Also **Fit to window** (rows sized so the visible hours fill the window height, columns split the width with a 40 px minimum; sliders and the fill checkbox ignored/disabled while on, recomputed on window/sidebar resize), plus Reset. Per-browser prefs (`rowH`, `colW`, `fillW`, `fit`); changing zoom keeps the view centred on the same spot; **printing ignores zoom** (print renders the grid at the default 48 px / 110 px scale via `withPrintScale`). Zoom/scroll affect only the calendar grid — the sidebar (and its narrow-screen behaviour) is deliberately unchanged **[U]**.
- **R-GRID-08** **[U]** **Scrolling:** the time column and the day headers are sticky (the top-left corner cell is sticky both ways) and the grid's scrollbars are always visible (`overflow:scroll`, styled scrollbars). `100dvh` is used so mobile browser bars don't hide the bottom of the grid.
- **R-GRID-09** **[U]** An **"N hidden" pill** (bottom-right of the grid) counts only event occurrences that are not shown *purely because* they fall in the hidden early hours or on the hidden weekend. Occurrences that are even partially visible (e.g. 04:00–06:00, or Fri 22:00 → Sat 02:00 with the weekend hidden) are never counted, and neither are occurrences hidden by the people filter or a hidden schedule. Tooltip gives the weekend / early-hours breakdown; click opens Settings.
- **R-GRID-10** **[C✓]** Layer order in a day column: phase backgrounds → hour lines (drawn *over* phases, **[U]**) → events → overlap stripes (in the day column, over the boxes' colours, under all event text) → now line.

## 3. Events
- **R-EVT-01** **[U]** Rounded boxes with a background colour, like Google Calendar. Created by dragging on empty space of a day (a plain click/short drag creates a 1-hour event) **[C✓]** or with the **+** toolbar button **[U]**. Can be removed, moved up/down within a day, moved to other days, resized, and may overlap other events.
- **R-EVT-02** **[U]** Fields: title (required), description (optional), person responsible (optional, a dropdown fed by the People list), persons involved (multi-select from the same list), colour, and **at least one schedule**. Toggling a schedule shows/hides its events.
- **R-EVT-03** **[U]** **Event box layout (rows):** row 1 = responsible person's icon (only if there is one, just before the title, sized to the text) + title on the left, the **time range right-aligned**, then the status icons (repeat / ⚠ / lock, top-right, **[U]** unchanged); row 2 = `By: <responsible name>` (no icon, left) and, right-aligned on the same row, `With: <involved people with icons>`; **no description row — the description is never shown in the compact grid view (event boxes, print schedule, print day view); it appears only in the peek card, the agendas and the dialog [U]**. Person icons inside event boxes are small (10 px glyph on a white disc) **[U]**. Continuation pieces show `from Fri 22:00 · until 02:00` as their time.
- **R-EVT-04** **[U]** Status icons top-right of the box: the **activity type icon** (R-EVT-11), **repeat icon** (event has >1 repetition), **[C✓]** ⚠ (repetitions of this event overlap each other), lock icon (locked).
- **R-EVT-05** **[U]** **Clipping:** event boxes render the *By/With* row only if it fits completely (`fitBox`, measured after layout; otherwise it is dropped). When anything is hidden (that row dropped or the title ellipsised) the box shows a small **⋯** marker plus a faint bottom fade (`.clipped`). **[U]** **Peek card** (mouse hover ~0.35 s over an event, locked ones included — hit-tested at column level, up to 3 stacked overlapping events): title (colour chip, responsible icon), time, `By: …`, `With: …` (icons), full description, schedules, ⚠ and lock notes, then a gap and the UI-behaviour instruction lines (for repeating events: "Dragging changes all repetitions; hold Shift to change only this one."; the number of repetitions is deliberately not shown). The peek card replaced the native tooltip (events keep an `aria-label`); it is hover-only — on touch a tap opens the dialog, which shows everything.
- **R-EVT-06** **[U]** Dialog **Delete** is a single button: removes the whole event including all repetitions and closes the dialog (no confirmation, no "delete all repeats" wording).
- **R-EVT-07** **[U]** **Copy** lives in its own dialog (opened by the "Copy…" button of the event dialog, or by **right-click** on the grid **[C✓]**): choose destination schedule and colour (same colour / same hue brighter-or-darker / random / chosen). Default: tweak when the destination already contains the event, otherwise same colour **[U]**. A copy is an independent event (to share one event, tick several schedules) — the dialog says so **[C✓]**.
- **R-EVT-08** **[U]** Event opacity = highest opacity among its visible schedules.
- **R-EVT-09** **[U]** Overlapping events that are drawn on top of each other (see R-EVT-10 for which ones): the overlapped range is drawn as **diagonal stripes mixing the overlapping colours** (45°, 7 px bands, 85 % of the highest opacity among the overlapping events), within that lane only. **[C✓]** Same-colour overlaps get a lightened stripe so they stay visible.
- **R-EVT-10** **[U]** **Side by side vs on top:** stripes mean "possible conflict", side by side means "in parallel, fine". Two overlapping occurrences in a day column **clash** — drawn **on top of each other with stripes** — when they **share a person** (responsible or involved, in either role; people *on call* don't count, R-EVT-16) **[U]**, belong to the same event, or either has **no responsible person** (even with involved people: they are busy, and nobody else is assigned, so it concerns everyone) **[U]**; otherwise they are **parallel** and go **side by side**. Decided per occurrence (each repetition has its own responsible person) and from visible occurrences only (people filter, hidden schedules). Layout (`laneLayout`): each group of time-overlapping occurrences splits the column into as many lanes as it needs (non-overlapping events keep the full width) **[U]**; lanes are ordered by the People list as shown (responsible person; reorderable, R-PPL-02; external people after ours, R-PPL-04), then start time. Each occurrence gets a **range of lanes** (R-EVT-13). Lanes are computed, never stored: dragging sideways within a day changes nothing. Click/drag/resize/peek/right-click hit-testing uses the pointer's x (`laneMap`, `inLane`, `fxAt`), so side-by-side events open/move directly without a chooser. **[C✓]** Settings → View *Show parallel events side by side* (`prefs.side`, default on; off = everything overlaps with stripes as before). When lanes get narrow, raise the column width (R-GRID-07) and scroll sideways. Background activities of external people (R-EVT-17) are not boxes and take no part in this at all.

## 4. Repetitions
- **R-EVT-13** **[U]** **Spanning lanes:** an occurrence that clashes with two (or more) occurrences that are parallel to each other **spans their lanes** instead of merging them: the parallel ones stay side by side and the spanning one overlaps each **independently**, striped only inside that lane (stripes are computed per group and lane; identical neighbouring lane segments are joined). Rule: parallel + overlapping ⇒ lane ranges disjoint; clashing + overlapping ⇒ ranges share a lane. Algorithm: occurrences that are not spanners are bundled (transitive clashes) and packed into lanes; each spanner takes the range from the leftmost to the rightmost lane of what it clashes with; the result is validated. **Lanes may be reordered** (all orders of up to 6 lanes, tried in order of closeness to the People order, People order first) so that the occurrences a spanner clashes with become neighbours **[U]**. Settings → View, nested under *Show parallel events side by side*: **Keep lanes in the order of the People list** (`prefs.sideFix`, default off, disabled while side-by-side is off) **[U]**. When no order works (or with the fixed order, or >6 lanes, or >60 occurrences in one group) that group **falls back to merging** its clashing occurrences into shared lanes with stripes — a deliberately distinct "something is wrong here" signal **[U]**. Groups in which nothing is parallel are one lane without any search. Hit-testing uses the range (`laneMap` = `[first, last, lanes]`); `data-lane` is `l/n` or `l0-l1/n`.
- **R-EVT-11** **[U]** **Activity type:** each event has **at most one** activity type (`type` = a type id, stored only when set), for the **whole event** (not per repetition) **[U]** — one type per event so a later per-person statistics view can put every minute in exactly one bucket. Dialog: an *Activity type* list (`#fTy`, `(none)` first, then the workspace's types; the chosen type's icon is shown beside it). The type's **icon is the first status icon** on every box (R-EVT-04); peek card, agenda and `aria-label` name it (icon in the type colour). Boxes keep the **event's own colour** — the type colour is for statistics only **[U]**. A type with the **soft look** (default: Free time) draws its events as free time was drawn before **[U]**: a soft tint of the event colour (`color-mix` with `--card`, follows light/dark, prints light), a solid 4 px colour edge on the left, dark text without shadow (`.ev.soft`). Otherwise typed events behave like any event — **the overlap rules (R-EVT-09/10) do not change [U]**. This **replaced** the earlier *Free time* checkbox / `free:true` flag outright (no migration; unreleased app) **[U]**. Phases never carry a type **[U]**.
- **R-EVT-12** **[U]** **Flexible time** (name chosen over "tentative", which calendars use for "maybe/unconfirmed" **[U]**): the activity happens *around* the given times but may not take the whole slot. Stored **per repetition** (`slot.flex:true`, only when set) **[U]**. Dialog: it is one of the three choices of the *Timing* control (R-EVT-15), which sets every repetition and, when they differ, presses no segment and shows *Mixed (set per day)* under it; each Quick row and Advanced block has a toggle (`.fxt`) that opens a small popover for that repetition alone; a day ticked (or block added) while the control is not mixed gets its choice; Quick↔Advanced keep the marks. Drawn with a **2 px dashed border** **[U]** (`--dash`: light on dark colours, dark on light ones via `ink()`, a darker shade of the colour on soft-look boxes). Peek card, agenda and `aria-label` say *Flexible time (around these times)*. Independent of the activity type (it's about *when*, not *what*). Phases never have it. **Overlap rules do not change [U]**; drags keep the marks.
- **R-EVT-15** **[U]** **Flexible start/end** (*Inicio/fin flexible*): a task that may start a bit late and/or finish a bit early (e.g. work 09:00–17:00, fine to start any time until 09:30 and to wrap up from 16:45).
  - **Model [U]:** per repetition, `slot.fs` = flexible minutes *after the start*, `slot.fe` = flexible minutes *before the end* (15-min steps, stored only when > 0). The slot's `start`/`end` stay the **outer** times, so moving, past-midnight pieces and hidden-hour counting are unchanged. **Core** = `start+fs` … `end−fe` (`coreOf`, per piece `coreIn`); the parts outside it are the **margins**. **[C✓]** The core stays ≥ 15 min (`fitMg`: shrinks the end margin first, then the start margin); `parseData` snaps and clamps; the dialog refuses a save that would break it, naming the day (`errCore`). Phases never have margins.
  - **Both kinds of flexible time are kept [U]**, as one per-repetition choice, the **Timing** control (`#fTim`, a segmented control of three buttons whose value is in `data-v`: `''` / `edge` / `flex` / `mix`; *Horas* in Spanish — not *Horario*, which is the word for schedule): **Fixed** / **Flexible start/end** / **Flexible (around these times)** (R-EVT-12); mutually exclusive (`parseData` drops `fs`/`fe` on a `flex` slot). Choosing *Flexible start/end* shows *May start up to [list] late, and finish up to [list] early* (`#fFs`/`#fFe`: 0, 15, 30, 45 min, 1 h, 1 h 15, 1 h 30, 2, 2½, 3, 4 h; 15/15 by default) applied to every repetition; a margin of 0 is not stored, both 0 = fixed. **[C✓]** The per-repetition toggle opens a popover (`tmPop`: the three choices, plus the two lists for *Flexible start/end*); the toggle then shows `+30−15` and its tooltip spells it out.
  - **Drawing [U]:** the core is a normal solid box; the margins (`.mg.t` / `.mg.b`, children of the day column in the event's lane) continue it above/below with a **2 px dashed border in the event colour**, no border towards the core, and a **translucent tint** (30 %, 14 % for soft-look types); only the outer corners are rounded. **[C✓]** The **text sits in the core box** (not at the top of the whole window as first planned): the core must be drawn above every margin, so the text has to live in the core. A piece that is **all margin** (e.g. the part after midnight of an event whose end margin covers it) is drawn as a dashed box with the text (`.ev.mgo`). The time shown is the outer range (`09:00–17:00`); peek card, agenda and `aria-label` add *Start between 09:00 and 09:30 · Finish between 16:45 and 17:00* (`edgeNote`). The resize handle sits at the outer end; dragging a margin moves the event.
  - **Overlaps — only cores count [U]:** stripes (R-EVT-09) and the repetition ⚠ (R-REP-05, `overlapSet` via `ivs`) appear only where **core overlaps core**. **Side-by-side lanes use core times too [U]:** occurrences that touch only through margins are not in the same lane group, so both keep the full column width (the alternative — 15 flexible minutes putting a parallel event side by side, at half width, for its whole length — was rejected). Margins follow their event's lane.
  - **Drawing order [U]:** every margin is inserted **before every core box** in the day column (after the hour lines), so a core always covers the margins of other events — **hidden entirely, dashed outline included**. Margin on margin: the tints mix, each keeps its dashed edges, the later-starting one on top (fallback if it ever looks messy: show only the top margin's tint there). **Hit-testing** (`piecesAt`): where a core is under the pointer, only cores count — a core over a margin opens/drags/peeks the core's event directly; margins alone behave like any overlap (chooser). Known side effect: resize handles stay above every box (bug 6 in §14), so the last ~9 minutes of an event's window still grab its handle even where another core covers its end margin.
  - **Statistics [U]:** margins count as **planned** time and are added to the hatched *of which flexible* part. **[C✓]** Double-booked time: a core beats a margin (the core's event gets that time); margin vs margin is split evenly; the *Overlapping* line and its places count only core on core.
  - **Dragging [C✓]:** moving keeps the margins; resizing (also "all repetitions" and *Only this day*) keeps their lengths, shrinking them if the core would drop below 15 min. Dragging the core's own edges may come later.
- **R-EVT-16** **[U]** **Involved people only on call** (`event.oncall:true`, only when set; per event, like `involved`): the involved people are *available, not busy* — e.g. Ann at hand to answer the cleaner's questions. Dialog: checkbox **Involved people are only on call** under *Persons involved* (`#fOnCall`, tooltip explains). Effects: in the **clash rule** (R-EVT-10, `pplOf`) only the responsible person counts as shared, never the involved ones (same event and *no responsible person* still clash); in **statistics** the involvement doesn't count, even with *Include time as involved person* **[U]**; box row 2, peek card, agenda and `aria-label` say **On call:** (*De guardia:*) instead of *With:*. The people filter (`slotVisible`) is unchanged.
- **R-EVT-17** **[U]** **Background activities** (`isBg`): an occurrence whose responsible person is **external** (R-PPL-03) and whose event has **no involved people, or only on-call ones**, is drawn as a **strip** (`.bgs`, 14 px, event colour) instead of a box **[U]** — the cleaner "just happening" without bothering anyone. Strips sit at the **right edge** of the day column; **[C✓]** a column with strips reserves a gutter (`--gut` on `.day`, `gutMap`; 16 px per strip sub-lane) that boxes, margins, stripes and handles stop before, so boxes lose a few pixels rather than half their width; overlapping strips are packed side by side in the gutter (`data-strip="k/n"`). Strips **never take part in lanes or stripes** and never make anything clash (excluded from `laneLayout` before it runs). **Looks like a lip [U]:** the first strip is flush with the column's right edge, right corners rounded and left corners straight (a mirrored phase lip; a piece cut at midnight keeps only its outer right corner rounded), and it shows the **title vertically, reading top-to-bottom** (`writing-mode:vertical-rl`, no rotation; 10 px bold, ellipsis, `textContent`), in `ink()` colour **[U]**. Phase lips deliberately keep reading bottom-to-top **[U]**. The rest (person, times) is in the peek card and `aria-label`; the ⚠ of overlapping repetitions only in the peek card. Flexible start/end shows as a lighter part (gradient) and the title starts where the solid core starts; flexible time is a dashed strip; dashed and all-margin strips use the page text colour. Interaction like any event (hover peek, tap/click opens, drag moves, bottom handle resizes, locked = click-through, inert in Phases mode); hit-testing by x: `laneMap` holds `['s', from, to]` in px from the right edge (sub-lane k owns `[16k, 16k+16)`, so strips and boxes meet without a gap) and `inLane` (which now gets the day) keeps boxes out of the gutter, using the column width `fxAt` measured (`fxW`). An external-led event whose involved people are **not** on call (a babysitter with Lucía) is a **normal box** with the normal rules, so it clashes through Lucía.
- **R-REP-01** **[U]** An event can repeat on chosen days of the week. Each day defaults to the general times but can differ; each repetition can have its **own responsible person**; all share colour/title/etc. Repetitions can be removed or retimed individually (dialog), and deleting the event deletes all.
- **R-REP-02** **[U]** Event dialog has two modes (tabs): **Quick** (default; Mon–Sun rows, one block per day) and **Advanced** (list of blocks: day, start, end, person, ✕, "+ Add block"; several blocks per day allowed). Quick→Advanced converts; Advanced→Quick is allowed only while no day has two blocks, otherwise the Quick tab is disabled with an explanatory tooltip. An event whose slots contain a duplicate day always opens in Advanced.
- **R-REP-03** **[U]** Events may **run past midnight**: end up to `MAXEND = 2880` (midnight at the end of the *next* day). Overflow stops at the next day; **Sunday wraps into Monday**. Drawn as joined pieces with flat edges; labels `22:00–02:00 (Next day)` / `from Fri 22:00 · until 02:00`. Only the last piece has the resize handle.
- **R-REP-04** **[U]** End-time select labels: `…23:45`, `00:00 (Next day)`, `00:15 (Next day)` … `23:45 (Next day)`, `00:00 (Day after next)`; entries ≤ start are disabled. Compact displays (boxes, agenda, tooltips): plain midnight → `00:00`; any later end → `(Next day)` suffix, including the end of the next day (`00:00 (Next day)`). *Known inconsistency between select and compact notation — alignment proposed, not done* **[P]**.
- **R-REP-05** **[U]** **Overlapping repetitions are allowed but warned about**: ⚠ on the affected dialog rows + summary line; ⚠ icons on the grid pieces; a toast when a drag/resize *creates* new overlaps (with Undo).
- **R-REP-06** **[U]** **Drag/resize of a repeating event changes ALL repetitions by default** (live preview), **Shift** (also mid-drag) changes only the grabbed one. After an "all" drop a toast offers **Only this day** and **Undo**. Moves shift every repetition by the same minutes and days (mod 7); resizes change every end by the same amount; **minimum duration is 15 minutes — a repetition is never removed by resizing**. Dragging a resize handle into the next day's column extends past midnight. Quick events block moving a single repetition onto a day that already has one; Advanced events allow it.
- **R-REP-07** **[U]** No confirmation dialog for repeat drags (an earlier confirm dialog was rejected).

## 5. Choosing among overlapping things (click vs drag)
- **R-SEL-01** **[U]** **Click** (open dialog): if everything under the pointer belongs to one event (even several overlapping repetitions) the dialog opens directly; if different events overlap, a small list shows each event once (repetitions grouped). "Under the pointer" means the same time *and* the same lane: events side by side (R-EVT-10) never trigger a chooser for each other.
- **R-SEL-02** **[U]** **Drag** (move or resize): if more than one event *or repetition* could be meant (bodies for moves; bottom ~9 min for resizes) a chooser lists each repetition separately (with its day/times). **[C✓]** The pick becomes the **selection** (`selK={id,i}`): outlined and raised above neighbours; the next drag that starts where it is a candidate acts on it directly. Esc, a click on empty space, or undo/redo clears it. (Two-step by design: you cannot choose while the button is held.)
- **R-SEL-03** **[C✓]** Right-click on a day column lists events/phases under the pointer → Copy dialog.
- **R-TOUCH-01** **[U]** **Touch (Google-Calendar style, mouse behaviour unchanged):** dragging scrolls natively (`touch-action:pan-x pan-y` on day columns/lanes); a **tap** opens an event (or the chooser if several events overlap); a **long-press (0.4 s, vibration tick)** on empty space starts creating an event, on an event starts moving it, on its bottom handle starts resizing (handle hit area is 16 px on coarse pointers). `press()` implements it; `touchmove` is `preventDefault`-ed only while a long-press drag is active. The native long-press context menu is suppressed, so **right-click Copy has no touch equivalent** (Copy… in the event dialog works; locked events can't be copied on touch) **[P]**.

## 6. Schedules
- **R-SCH-01** **[U]** Multiple schedules overlay the same calendar; each can be shown/hidden with an **eye icon** (open eye / dashed eye) **[U]**, has a name, colour, a small **calendar icon** in its colour **[U]** and an **opacity slider** (with a checkered-box icon + tooltip) **[U]**.
- **R-SCH-02** **[U]** **Locked schedules:** an event is locked only if *all* its schedules are locked **[C✓]**; locked events can't be selected/moved/dragged/edited, are click-through (so events beneath stay reachable) **[C✓]** and show a lock icon; they can still be copied via right-click **[C✓]**.
- **R-SCH-03** **[C✓]** Row menu (⋯): colour, opacity, lock/unlock, **"Show only this one"** (solo), delete (events only in that schedule are deleted too, with confirmation). Solo + two schedules ("Week A", "Week B") is the **documented workaround for a two-week rota**; a real two-week feature was judged too complex and is deliberately not built **[U]**.
- **R-SCH-04** **[U]** The first-run schedule is named **Routine**.

## 7. People
- **R-PPL-01** **[U]** A People list "created in the same fashion as schedules": name, colour, icon, eye (show/hide). **Visibility rule (`slotVisible`) — viewing a person's calendar:** an occurrence with **no responsible person is always shown** (unless its schedule is hidden), whatever its involved people; otherwise it is shown when its responsible person is shown **or** any involved person is shown. So viewing a single person shows everything except occurrences led by someone else in which that person is not involved. (With nobody shown, only occurrences without a responsible person remain.) Rule is per repetition, since each repetition has its own responsible person. Deleting a person removes them from all events. Person ⋯ menu: Colour…, Statistics… (not for external people), External (not one of us), Delete.
- **R-PPL-03** **[U]** **External people** (`person.external:true`, only when set): someone from outside the household — a cleaner, a gardener, a babysitter — who does activities but isn't "one of us" **[U]**. Toggled in the person ⋯ menu (*External (not one of us)*, tick + explanatory tooltip, undoable data); the row shows a small external-link marker (`.extb`, labelled). Their rows are listed in the **External** sub-group of the People section (R-PPL-04). They stay normal people otherwise: own eye (visibility rule unchanged), responsible/involved lists (the responsible list adds *(external)*), lane order (after ours). **Left out of the statistics** (person picker, *Everyone*, its table; `ourPeople()`); only external people → the "add people first" toast. Activities they lead alone are background strips (R-EVT-17). `parseData` keeps the flag only when `true`; it travels with files, links, insert, transfer (a person created in the target keeps it) and anonymised exports.
- **R-PPL-02** **[U]** **Reordering people:** each person row starts with a **grip** (six dots, shown on hover; always faintly visible on touch screens) — drag it up/down (drop line shows the target) or focus it and use the **arrow keys**. The order is data (undoable, unsaved) and sets the order of side-by-side lanes (R-EVT-10/13) — the order *as shown*, i.e. our people first, external people after them (`pIdx` in `laneLayout`). Other lists are not reorderable yet.

## 8. Phases and rhythms (background day-structure)

- **R-PHS-03** **[U]** Phase fields: name, description (optional), colour, ≥1 rhythm; **no people**. Repetitions stay within one day; same Quick/Advanced dialog as events; a phase can belong to several rhythms and be copied to another rhythm (same Copy dialog).

- **R-PHS-08** **[U]** **Default first-run rhythm** (also after Clear memory and for a new workspace): a **visible** "Normal rhythm" with **7 parts of the day**, the same times every day, no descriptions (`defaultRhythm()`): Midnight 00:00–05:00, Early morning 05:00–08:00, Morning 08:00–12:00, Noon 12:00–14:00, Afternoon 14:00–18:00, Evening 18:00–21:00, Night 21:00–24:00 (Spanish: Madrugada, Primera hora, Mañana, Mediodía, Tarde, Atardecer, Noche). ## 10. Persistence and data
- **R-DATA-01** **[U]** **Workspaces:** several named, fully independent data sets (schedules, people, activity types, events, rhythms, phases) live in memory at once; the sidebar has a **workspace switcher** under the title (menu: switch, *New workspace…*, *Rename current…*, *Duplicate current*, *Delete current…*; • marks unsaved ones; the last workspace can't be deleted). `S` always points to the current workspace's data; `WS=[{id,name,data,lb,lf,undo,redo}]`, `curId`; `syncWs()` writes the live `S`/history back into the record before switching/saving; **undo/redo history, selection and dirty state are per workspace**. A *new* workspace starts from `defaultData()` (Routine schedule + default activity types + Normal rhythm); *Duplicate* copies the data and counts as unsaved.
- **R-DATA-02** **[U]** **Save…** asks the target (browser memory / JSON file — encrypted by default, unencrypted on request (R-SHARE-07) / password-protected shareable link). **Files and links always hold exactly one workspace (the current one) [U]**; only **browser memory** asks, when there is more than one workspace, **which to save: only the current one or all** (browser memory itself stays unencrypted — locking it with a passphrase is deliberately postponed [U]). Browser memory (`localStorage` key `weekly-schedules-workspaces`, `{version:1,current,workspaces:[{id,name,…data}]}`): *current only* updates/inserts just that workspace's entry (other stored entries stay as last saved); *all* rewrites the whole store (deleted workspaces disappear). The (decrypted) content of a file/link is one workspace record `{version:1,id,name,schedules,people,types,events,rhythms,phases,phaseOpacity}` (`buildFile`, `parseWorkspace`).
- **R-DATA-03** **[U]** The app **auto-loads all workspaces from browser memory** at startup. **Load → Browser memory** reverts the *current* workspace to its saved copy (undoable). **Load → JSON file** and **opening a shareable link** never overwrite anything silently: both go through one **import dialog** (`openImport`) for the single workspace they contain, with exactly three options: **Import as a new workspace** (default; name made unique; keeps the file's id when free), **Insert into the current workspace** (its schedules, people, rhythms and phases arrive as *new* items with new ids; name clashes get "(2)"; inserted rhythms are hidden unless none was visible) or **Replace an existing workspace** — a single option that opens a picker listing *all* workspaces (best candidates first) with flags for the *active* one, the one with the *same id* and the ones with the *same name* (`pickReplace`), followed by a **confirmation naming the workspace that will be replaced** (`confirmReplace`). There is deliberately no separate "replace current" or "replace matching" option. After importing or replacing, the app switches to that workspace. **Nothing is ever merged** (no occurrence/event merging, no conflict resolution) **[U]**. Replace/insert are undoable in the affected workspace; imported-from-file workspaces count as saved (file), imported-from-link ones as unsaved. A first-time visitor with no browser memory and an untouched default workspace opening a link adopts it directly (`adoptWs`).
- **R-DATA-04** **[U]** **Copy/move between workspaces:** schedule and rhythm rows have *Copy or move to workspace…* (`openTransfer`): a **schedule** goes with all its events (attached only to the new schedule); a **rhythm** goes with all its phases; **individual phases cannot be copied or moved to another workspace [U] — only whole rhythms (with their phases)**; the Copy dialog for a phase only offers rhythms of the current workspace. For schedules, every person referenced by the events (responsible per repetition, involved) is listed in a **people mapping dialog** (`askPeople`): *create that person in the target*, *use an existing target person* (default: same name, case-insensitive; otherwise create), or *leave blank* (no responsible person / not involved). Copies get unique names in the target; both workspaces get an undo step; *move* removes the item from the source afterwards (schedule: events only in it are deleted; phase/rhythm likewise).
- **R-DATA-05** **[U]** **Clear memory** (confirmation) deletes the whole store (all workspaces) **and restarts the app** with one default workspace. **Restart** discards unsaved changes in all workspaces and reloads browser memory. `beforeunload` warns when *any* workspace has unsaved changes; a workspace is dirty when its data differs from both its last browser save and its last file save; the sidebar title shows • when any is dirty.
- **R-SHARE-01** **[U]** **Protected links and files** (reason: the data may describe vulnerable people such as children or the elderly): **links always require a password — there is no unencrypted link [U]**; JSON files are encrypted by default and only unencrypted when the user explicitly chooses so (R-SHARE-07). Save… → *JSON file* / *Shareable link* open one dialog (`openProtect`) with the options and the password field. Without `crypto.subtle` (old browsers/insecure contexts) links and opening encrypted files are refused with an explanation — never a plain fallback; the file dialog then only offers *Unencrypted* (with its warning, still a deliberate click on Save file).
- **R-SHARE-02** **[U]** *Leave out personal details* checkbox (unticked by default): people become "Person 1", "Person 2"… and event/phase descriptions are removed — `anonymised()`; titles and schedule/rhythm/workspace names are kept and the dialog says so; an anonymised export is **not** treated as a backup, i.e. it doesn't mark the workspace as saved to file.
- **R-SHARE-03** The password field is pre-filled with a generated password (`genPassword`: **25 random characters in 5 groups of 5**, unambiguous alphabet without 0/O/1/l/I, unbiased `crypto.getRandomValues`, ~145 bits) that can be regenerated or replaced; any password must be **at least 20 characters** (trimmed). The dialog tells the user to give the password to the other person by a *different route* than the link/file; the result dialog has *Copy* buttons for link and password.
- **R-SHARE-04** Crypto (`seal`/`unseal`, Web Crypto, no libraries): JSON → raw-deflate (if `CompressionStream` exists; flagged inside) → **AES-256-GCM** with a key from **PBKDF2-SHA256, 600,000 iterations**, random 16-byte salt and 12-byte IV per export; blob = `[1][iterations u32][salt][iv][ciphertext+tag]` with the header authenticated; decryption refuses iteration counts outside 100k–2M (crafted-file DoS), wrong passwords and altered data fail cleanly, and the decompressed size is capped at 2 MB.
- **R-SHARE-05** **Links:** `<app url>#data=e1.<base64url blob>` — in the URL fragment, which is never sent to web servers and not fetched by link previews; the result dialog shows the link and the password, the length (warning above 8,000 characters) and a `file://` note. **Opening:** `askPassword` (masked, show toggle, retry on wrong password); links are only understood in the `e1.` form and re-checked on `hashchange`; the fragment is removed from the address bar after success or cancel. After decryption the content goes through the normal import dialog (or is adopted by a pristine first-time visitor). Invalid/too-large links show a toast and change nothing.
- **R-SHARE-06** **Files:** `{format:'weekly-schedules-encrypted',version:1,data:<base64url blob>}` named `weekly-schedules-<date>-encrypted.json` (the name deliberately doesn't reveal the workspace). Opening a file asks for the password (retry on mistakes); encrypted files and *plain* hand-written JSON files can both be imported (`weekly-schedules-encrypted` container detected by `format`). The dialog title is *Save JSON file*.
- **R-SHARE-07** **[U]** **Unencrypted JSON files (files only, never links [U]):** the JSON-file dialog has a switch **Encrypted (recommended)** (default, every time — the choice is never remembered) | **Unencrypted**. Unencrypted hides the password field and shows a warning box (`plainWarn`): anyone who gets the file can read everything, including plans of possibly vulnerable people (forwarded email, shared/cloud folder, lost USB stick, shared computer); use it as a private backup and prefer encryption or *Leave out personal details* when sending it. The file is the readable workspace record (`buildFile`, the same shape plain imports accept) named `weekly-schedules-<date>.json` (no `-encrypted`); it counts as a backup (marks the workspace saved to file) unless anonymised; it opens without a password through the import dialog. `saveFile(null, anon)` = unencrypted.
- **R-DATA-06** **[U]** **View settings are per browser, not in the save file** (`prefs`, key `weekly-schedules-prefs`): `showEarly`, `clock12`, `hideWeekend`, `side`, `sideFix`, `theme` (`auto`|`light`|`dark`), `rowH`, `colW`, `fillW`, `fit`, sidebar width/collapsed, section collapse flags (`secSch`, `secPpl`, `secTyp`, `secRh`, `secZoom`, and `secExt` for the External people sub-group, folded unless `false`). Data and view state are separated; *within* the file, `schedules[].visible/opacity`, `people[].visible`, `rhythms[].visible` and `phaseOpacity` are view state (saved, but ignored by `dataKey()` and preserved across undo).
- **Workspace data shape** (used inside the browser store, in files and in links):
```
schedules [{id,name,color,opacity,locked,visible}]
people    [{id,name,color,visible,external?}]   (external: true or absent)
types     [{id,name,color,icon,soft?}]   (icon: a TICONS key; soft: true or absent; colour for statistics only)
events    [{id,title,desc,color,type?,oncall?,schedules:[id],involved:[personId],slots:[{day,start,end,person,flex?,fs?,fe?}]}]   (type: a type id or absent; oncall: true or absent; flex: true or absent; fs/fe: flexible minutes after the start / before the end, > 0 or absent, never with flex)
rhythms   [{id,name,visible}]
phases    [{id,title,desc,color,rhythms:[id],slots:[{day,start,end}]}]
phaseOpacity 0.05–1 (default 0.3)
```
**R-DATA-07** `day` 0 = Monday; times in minutes on a 15-min grid; event `start` 0–1425, `end` ≤ 2880; phase `end` ≤ 1440. `parseData()` is the single place that validates/sanitises input (clamps ranges, hex colours only, string length caps, drops events/phases without repetitions). **No backwards compatibility with earlier development formats is kept [U]** — the app hasn't been released, so there are no legacy keys, shapes or migrations; when the format changes after release, add a versioned migration then. Callers assign `S` themselves.

## 11b. Security (threat assessment decisions)
Threat model: a static, client-only app (no server, accounts, network calls or third-party code); the data at stake is personal schedule information in the browser and in shared files/links. Decisions **[U]**:
- **R-SEC-01** **Content-Security-Policy** `<meta>` in the page: `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; connect-src 'none'; base-uri 'none'; form-action 'none'`. Even if an escaping bug let foreign code run, it could not contact other sites or load outside content. `'unsafe-inline'` is needed because everything is one file, so the policy does *not* stop an injected inline script by itself (a build step with hashed scripts could tighten it later). `frame-ancestors` (clickjacking) can't be set from a meta tag on GitHub Pages — accepted, low impact. **Any new resource type (fonts, images from URLs, workers, network calls) needs a deliberate CSP change; check the browser console for "Refused to…" messages after edits.**
- **R-SEC-02** **Escaping rule:** every piece of user-controlled text that goes into `innerHTML`/`insertAdjacentHTML` must pass through `esc()` (escapes `& < > " '`); prefer `textContent`/DOM properties. Imported colours are reduced to `#rrggbb` (`normHex`), names/titles capped at 200 and descriptions at 5,000 characters.
- **R-SEC-04** **Nothing leaves the device** (except files the user downloads: the JSON export and the statistics CSV, the only two `Blob`s): no `eval`, `new Function`, `document.write`, `fetch`/XHR/WebSocket/`sendBeacon`/`window.open`, no cookies, no third-party code; only the two documented `localStorage` keys are written.
- **R-SEC-03** **Import limits** (`LIM`, files and links only, never the browser store): 100 schedules, 500 people, 100 activity types, 5,000 events, 100 rhythms, 2,000 phases, 200 repetitions per event/phase; links additionally capped at 2 MB when decompressed. Exceeding a limit rejects the import with a clear message.
- **Link/file privacy:** links are always encrypted with a user-visible password, exported files too unless the user deliberately picks *Unencrypted* after a warning (see §10); the data sits in the `#` fragment. Limits that remain: whoever has link *and* password can read and forward it (no revocation/expiry without a server), a short or reused password can be guessed offline (hence the generator and the 20-character minimum), the link length hints at the amount of data, imported/saved data is plaintext again in browser memory and in memory-only exports such as an anonymised copy's source, and a tampered hosted page could capture typed passwords (repo/hosting protection).
- **R-SEC-05** **Hosting advice (not code):** on GitHub Pages all sites of one account share the origin `name.github.io`, so other pages there can read this app's saved data → prefer a custom domain or a dedicated account/organisation; protect the repository (two-factor sign-in, protected main branch, HTTPS enforced) because whoever can change the code can read users' local data. Browser storage is unencrypted (shared computers: use Clear memory; keep JSON backups).
- **Automated checks:** see §14 (`npm test`, `npm run test:e2e`). Re-run them after every change that touches HTML building, import or links.

## 13. Code map (everything is in `index.html`)
- State `S` (data) + `prefs` (view). `render()` rebuilds the grid; `renderSide()` rebuilds the sidebar (skipped while dragging an opacity slider via `skipSide`).
- Time helpers: `fmt`, `fmtEnd`, `endLabel`, `piecesOf` (event → per-day pieces), `coreOf`/`coreIn`/`fitMg`/`edgeNote` (flexible start/end), `overlapSet` (week-wrapped overlap detection of cores), `piecesAt/handlesAt` (hit-testing, polymorphic for events/phases via `act()`, `eVis`, `eLock`, `sVis`).
- People outside the household and background strips: `isExt`, `ourPeople`, `isBg`, `pplOf` (on-call rule); strips are drawn in `render()` after the boxes (`bgs`, `gutMap`, `SW` = strip width); the People sidebar splits `ourPeople()` and the `.extg` sub-group.
- Side-by-side layout: `laneLayout` (clash/parallel matrices, groups, spanners, lane-order search, fallback; R-EVT-10/13), `laneMap` (last drawn lane ranges, keyed `eventId|slotIndex|piece`) read by `inLane`; boxes and stripes carry `data-lane="l/n"` or `"l0-l1/n"` (tests read that, since jsdom rewrites the `calc()` positions).
- Interaction: `grab` (disambiguation) → `startDrag` (move/resize, all vs Shift) / `startCreate`; `overlapMenu` (choosers, optional grouping); history: `hist()` *before* mutations or `pushUndo(before)` for drags; `restoreState` preserves view state.
- Dialogs: `openDlg` (kind inferred: event/phase), `openCopy`, `xdlg` (generic modal), `pickColor`, `openSettings`, `openHelp`, `showAgenda`.
- **Dialog chaining gotcha:** a button handler of `xdlg` that opens another dialog used to get it closed again right away (the first dialog auto-closes after the handler). `xdlg` now tracks the current dialog (`xTok`) and skips the auto-close when a handler replaced it; chained flows additionally defer with `setTimeout(…,0)`. Always test dialog flows by *clicking the real buttons*, not by calling the functions directly (that is how this bug slipped through once).
- Persistence & workspaces: `parseData` (validation of one workspace), `parseWorkspace`, `buildFile`, `keyOf`/`wsDirty`/`anyDirty`, `loadStore`, `saveMem(scope)`, `saveFile()`, `saveTo(target)`, `openShare()`/`handleShareLink`, `openImport`/`pickReplace`/`confirmReplace`/`applyImport`/`insertInto`/`adoptWs`, `switchWs`/`syncWs`/`addWorkspace`/`wsMenu`, `openTransfer`/`doTransfer`/`askPeople`/`mapTypes`, `restart`, `clearMem`, `initDefault`/`defaultData`/`defaultRhythm`.
- Activity types: `TICONS`/`tIcon`/`TYN`/`iconName` (icon set), `defaultTypes`, `tyOf`/`tyTag`, sidebar `iconMenu`/`tyMenu`/`delType`; list reordering `gripFor(row, list, item, group)` (People, per sub-group); the dialog list is `#fTy` (`updTyIc`). Event dialog timing: `timV`/`setTimV`/`timPick` (segmented `#fTim`), `updOc` (on-call row).
- Resize handles are *not* inside their boxes: each `.rz` is a child of the `.day` column positioned at the box's bottom (`translateY(-100%)`), sharing the box's pointer handler; tests reach it with `box._rz`.
- Static dialog translation gotcha: `applyStatic` re-translates every `[title]` in dialogs from the English it first saw (`__t`), by prefix; a title set from `L()` at runtime must also set `el.__t` to the translated text, or a shorter prefix key overwrites it (this once hit the flexible-time toggles).

## 14. Testing
**Run:** `npm install`, then `npm test` (Vitest 5 + jsdom, 1,025 tests, ~50 s), `npx playwright install` once (on WSL or a fresh Linux machine also `sudo npx playwright install-deps` once, otherwise Chromium can't start and *every* e2e test fails with `error while loading shared libraries`), then `npm run test:e2e` (Playwright, 145 tests, ~4 min; Chromium + a Pixel 5 profile for `touch.spec.js`; `ALL_BROWSERS=1` adds Firefox/WebKit, which have not been run yet), `npm run lint`. CI: `.github/workflows/tests.yml` (lint + fast tests + Chromium on every push, all browsers nightly).

**Layout**
- `tests/unit/` pure logic through the page's own functions (time, colours, visibility rules, validation, encryption, translations).
- `tests/app/` behaviour of the screens in jsdom: grid, events, repetitions, choosers, schedules/people, phases, workspaces, import/transfer, share, print/agenda, touch, UI.
- `tests/security/` CSP, escaping with hostile data on every screen, no risky APIs, no network, limits.
- `tests/e2e/` real browser: geometry (sticky, scrollbars, lips flush, zoom, fit), real mouse/keyboard interaction, phone touch, downloads/links/clipboard in two browser profiles, print to PDF, CSP enforcement, performance budgets, accessibility ratchet. `tests/e2e/serve.js` serves `index.html` on http://localhost:4173 (a secure context).
- `tests/helpers/app.js` jsdom harness: `openApp`, `setData`, `dragFrom`, `createDrag`, `fillDialog`, fake column geometry (`.day` n spans x 100n..100n+100, top 0), stubbed dialogs/crypto/downloads/clipboard/print.
- `tests/requirements.test.js` traceability + description quality.

**Rules**
- Every test group is named `R-AREA-nn <what is checked>` after a requirement in this file; individual test names must say what is expected (≥ 25 characters, no duplicates, no skip/only/todo). The console output is the documentation. New requirement → new ID here → tests.
- jsdom has no pointer-event handler attributes (`el.onpointerdown = f` is just a property), so jsdom tests call the handlers directly (`el.onpointerdown(fakeEvent)`, `col.onpointermove(...)`); document-level listeners do receive dispatched events. jsdom has no layout, so anything about sticky/scroll/real drag/print belongs in `tests/e2e`.
- Playwright's `page.evaluate` is exempt from the page's CSP (eval works there); to test `eval` blocking, inject an inline script that runs later (see `security.spec.js`). Headless Chromium never shows the real `beforeunload` dialog, so those tests fire the event and check `defaultPrevented`. Playwright hides scrollbars by default; the config keeps real ones (`ignoreDefaultArgs`).
- Touch in e2e: `Input.dispatchTouchEvent` with many small moves (`touch`/`swipe` helpers); `synthesizeScrollGesture` does not scroll here.
- Always test dialog flows by clicking real buttons (see §13 dialog-chaining gotcha).
- **Negative controls:** after adding tests for a behaviour, temporarily break the behaviour in `index.html` and confirm the tests fail. 53 key behaviours were checked this way (External people sub-group: folded by default, reordering within a group, lane order as shown; strips flush right with their title; dialog: on-call row only with involved people, Timing control shows Mixed; on-call clash rule and statistics, strips kept out of lanes, strip/box hit-testing by x, external people out of statistics and kept on transfer; flexible start/end: stripes, lanes and ⚠ only on cores, margins below cores, core wins hit-testing, core beats margin in statistics, margins shrink on resize; stats splitting of double-booked time, CSV formula guard, spanning lanes, lane reordering, soft-look rendering, type matching by name on insert/transfer, covered resize handles, side-by-side rule incl. involved people, lane-aware hit-testing, escaping, people filter, lock rule, week wrap, workspace save, right-click, touch drag, luminance contrast, anonymising, Shift, leave-page warning, CSP, password minimum, iteration bounds, decompression cap, midnight format, one visible rhythm, undo cap, import limit, print scale, sticky time column, lip alignment, scrollbars). Only a fraction of the tests has had this check.

**Bugs found by the suite and fixed (keep the tests)**
1. Saving with one workspace left did not drop deleted workspaces from browser memory (they came back after reload): `saveTo` now saves "all" when only one workspace exists.
2. Right-click on an event, phase or lip also started a drag/opened the edit dialog, hiding the copy menu: the pointer-down handlers ignore non-primary buttons.
3. A touch long-press drag of an existing event stalled after the first move (the redraw removes the touched element, so touch events no longer reached `document` and the browser started scrolling): `press()` captures the pointer on `body` and attaches a non-passive `touchmove` blocker to the touched element itself. Verified in Chromium touch emulation only — **try it on a real phone (Android Chrome and iOS Safari).**
4. Lip text colour is chosen by WCAG relative luminance (`lum`/`ink`), not HSL lightness (white text on yellow was ~1.6:1).
5. Clicking an existing phase in Phases mode did nothing when the workspace had people: `openDlg` read `involved` of the phase (phases have none) and crashed. Found by the user; the earlier tests used data without people.
6. A resize handle could be covered by an overlapping box: always for phases listed after the one being resized, and for events when the lower event's schedule opacity was below 100 % (opacity makes the box its own layer). Handles are now separate elements in the day column above every box (`.rz`, `box._rz`, `z-index:6`). Found by the user.

**Known issues (not fixed)**
- Accessibility (`tests/e2e/a11y.spec.js` is a ratchet: fails on new kinds or more elements; lower the numbers as you fix): unlabeled inputs (`label`: sidebar rename fields; the event dialog is now clean and its ratchet is `{}`), hour labels with low contrast (19), `#wrap` not keyboard-focusable (`scrollable-region-focusable`), selected Events/Phases button contrast in dark mode.
- Performance (this sandbox): drawing 1,000 events ≈ 0.6 s, 2,000 ≈ 1.6 s, 5,000 ≈ 3.9 s (superlinear). 5,000 events necessarily overlap heavily (≤ 96 non-overlapping per day), so the import limit is a safety cap, not a promise of smooth use. Budgets in `perf.spec.js`: 5,000 events < 15 s, 1,000 events < 3 s.
- Minor: a decompression bomb is reported as "not a valid save file" (the `'big'` branch of `askPassword` is never reached because `inflate` throws `'too big'`); a link with an empty payload asks for a password before saying it is invalid; the encrypted container's own `version` field is not checked (the version byte inside the blob is).
