## 1. Product
A single static `index.html` (HTML + CSS + vanilla JS, no libraries, no network requests) that must work when opened from disk or GitHub Pages. A weekly planner organised in **workspaces** (several independent named data sets in one browser), each with overlayable **schedules**, **events** with repetitions, **people**, and background **rhythms** made of **phases** (named parts of the day). English/Spanish UI. Repo files: `index.html`, `README.md`, `CLAUDE.md`.

## 2. Calendar grid
- **R-GRID-01** **[U]** Columns Monday→Sunday, left to right. Days are **not** attached to dates (it's a repeating week).
- **R-GRID-02** **[U]** Hourly rows from 05:00 to midnight by default; 00:00–05:00 hidden but can be shown (Settings → "Show early hours"). Events/phases in hidden hours are kept; they count in the "N hidden" badge (events only).
- **R-GRID-03** **[U]** **Saturday and Sunday: only the header cells have a different hue** (not the whole column). The hue covers just the header cell *between the day column's borders* — it must not extend into the phase-lip lane on the left, **except** the lane between Saturday and Sunday (both weekend headers), which takes the same hue so the two headers read as one band (class `wj`; the lane between Friday and Saturday stays neutral; the single-day print drops the join). Dark-mode variant exists (`--weh`).
- **R-GRID-04** **[U]** Settings: show/hide Saturday & Sunday columns; AM/PM clock; show/hide a red **now line** on the current weekday's column (updates every 30 s, default on, never printed).
- **R-GRID-05** **[U]** Midnight is always displayed as `00:00` (`12:00 AM` in AM/PM mode), never `24:00`.
- **R-GRID-06** **[C✓]** 48 px per hour, 15-minute snapping, hour lines, sticky day headers. Each day header shows an **agenda icon**; clicking the header opens that day's agenda **[U]**.
- **R-GRID-07** **[U]** **Zoom (grid scale and grid text size):** the sidebar's **Zoom section** (collapsible like the others, `secZoom`; never in Settings **[U]**; sliders have `aria-label`s, explanations are tooltips) holds, in this order **[U]**: **Fit width** (`fitW`, default on) with the **Column width** slider indented under it (`.zsub`; px per day, **70–1000**, default 110), **Fit height** (`fitH`, default on) with the **Row height** slider under it (px per hour, 24–120, default 48), a divider, **Text size** (`txt`, 80–160 %, step 10, default 100), and *Reset zoom* (both boxes on, 48 px, 110 px, 100 %). **Fit width** on = the columns share the window width (40 px minimum, scroll sideways below that); off = each column is **exactly** the slider width (a narrower week leaves empty space on the right, a wider one scrolls sideways — that is how to make room for side-by-side lanes, R-EVT-10). The former *Fill the window width* ("at least the slider width, stretched") made every value below window ÷ 7 look the same, so it was dropped **[U]**. **Fit height** on = rows sized so the visible hours fill the window height under the **measured** day header (it grows with the text; measured before the grid is emptied, since a layout of the empty grid would reset the scroll position; no layout → the slider value). A slider is **disabled while its Fit box is on and shows the fitted size** (`updZoomUI` after every render; `fitted`), and **unticking keeps that size** so nothing jumps **[C✓]** (a focused day is not a week column: unticking *Fit width* there keeps the slider value). **Text size** sets `--ts` on `:root` and `#grid`; grid text uses `calc(Npx * var(--ts,1))`: box text and its icons (and the room kept for the status icons), hour labels, day names, phase labels, the hover card and the Live View sizes (multiplied, R-GRID-12); the time column is `round(52 × ts)` px. **Lips and strip titles keep their size** (fixed-width lanes); the sidebar and dialogs never scale — that is the browser's zoom **[U]**. Per-browser prefs (`rowH`, `colW`, `fitW`, `fitH`, `txt`; the retired `fillW`/`fit` are no longer read); recomputed on window/sidebar resize while a Fit box is on; changing zoom keeps the view centred on the same spot; **printing ignores zoom and text size** (48 px / 110 px / 100 % via `withPrintScale`). Zoom affects only the calendar grid — the sidebar (and its narrow-screen behaviour) is deliberately unchanged **[U]**.
- **R-GRID-08** **[U]** **Scrolling:** the time column and the day headers are sticky (the top-left corner cell is sticky both ways) and the grid's scrollbars are always visible (`overflow:scroll`, styled scrollbars). `100dvh` is used so mobile browser bars don't hide the bottom of the grid.
- **R-GRID-09** **[U]** An **"N hidden" pill** (bottom-right of the grid) counts only event occurrences that are not shown *purely because* they fall in the hidden early hours or on the hidden weekend. Occurrences that are even partially visible (e.g. 04:00–06:00, or Fri 22:00 → Sat 02:00 with the weekend hidden) are never counted, and neither are occurrences hidden by the people filter or a hidden schedule. Tooltip gives the weekend / early-hours breakdown; click opens Settings. Never shown in Live View (R-GRID-12).
- **R-GRID-11** **[U]** **Focus on one day** ("laser focus"): each day header has a **focus button** (viewfinder icon, `.foc`, at the header's right; **shown on hover** and on keyboard focus, always on touch screens, so it doesn't make the day names wrap; tooltip *Show only Tuesday…* explains the way back); clicking the day name still opens the agenda (R-GRID-06). In focus only that day is drawn (`focusD`; `days = [focusD]`), **filling the window width** even with *Fit width* off (the row height, *Fit height* and text size still apply). The header (`.dh.fo`) shows **◀ day name ▶** (`.prv`/`.nxt`, `stepFocus`: wrap around Sunday→Monday, skip Saturday and Sunday while the weekend is hidden) and a **Week** button (`.wk`) that brings the week back, as does **Esc** when no event is selected (Esc first clears a selection; ignored while a dialog or menu is open). **[C✓]** View state that is **not remembered** (a reload shows the week; Live View, R-GRID-12, is the exception and has no arrows, Week or agenda buttons), not undoable, not an unsaved change. The **N hidden** pill counts only the focused day's occurrences in the hidden early hours. **Print** prints what is on screen: the day view (`printDay`) while focused, the week otherwise; the focus buttons never print. Everything else works as usual (create, move, resize, peek, choosers); moving an event to another day or resizing into the next day's column is not possible in focus — use the dialog. A help tip describes it.
- **R-GRID-12** **[U]** **Live View** (*Vista en directo*), for **a small screen (a tablet) left somewhere public so everyone can see what is going on now** **[U]**. **Controls in the sidebar, not on the grid** **[U]**: a full-width row under the icon toolbar (`.lvrow`) with **Live View** (`#lvB`, video-camera icon); while live it is red and reads **Stop Live View** (stop icon), and after a manual scroll a **Now** button (`#lvC`, crosshair) appears beside it. Starting it **jumps to today's single-day view** (R-GRID-11) from wherever you are. **The grid while live** (`#grid.lv`): **read-only: only scrolling, and tapping boxes to read them** **[U]** (capture listeners on `#grid` stop every pointer event before the boxes' own handlers — no dialogs, drags, new events, hover cards or right-click; resize handles hidden; `pointer-events:none` on the header and lip lanes; a press that moves less than 8 px is a tap, anything else is left to native scrolling); the day header shows **only the day name** (no ◀ ▶, Week, agenda or focus buttons, no agenda on click) **[U]**; **larger text** in the compact view (boxes 15 px, row 2 13 px, hour labels 13 px, day name 16 px, strip titles 12 px; all but the strip titles multiplied by the Zoom text size, R-GRID-07) **[U]**; **tapping a box opens a speech bubble** **[U]** (nothing pops up by itself — automatic bubbles for whatever the now line was over were tried and dropped, as was a separate cards column **[U]**): it **fades in quickly at the tap** (`lvin`), its triangular arrow pointing at the tap (`LV_SLACK`: up to 6 px off it where the column edge leaves no room, e.g. on a strip), and holds a larger hover card (`peekRows(it, true)`: title with person icon, time, type, flexible notes, *In the background*, *During* / *Also during this*, By, With / On call, description; no schedules, warnings or how-to lines) for **every occurrence under the tap**, found like any click (`piecesAt` on the events, lanes, strips, a nested box over its host, cores over margins): **where boxes overlap, one bubble with a section each** **[U]** (start order, divider, colour edge). **Several bubbles may be open** **[U]**; **each fades out a minute after it opened** (`LV_PEEK`) **[U]**, or at once with a **tap on it**, while a **tap on empty space closes them all** **[U]**. Open bubbles (`lvOpen`: occurrence keys, tap position as a fraction of the width and a minute) are redrawn after every redraw without fading in again; leaving Live View or midnight closes them. **Placement** (`lvDraw`): above or below the tap (never across its row), the arrow at the bubble's start, middle, end or as centred as the column allows, inside the column, plus tiers further away joined by a thin stem (`.lvstem`); the lowest score wins — another open bubble's area ×1000, the measured text rows of the boxes and strip titles (half weight over the bubble's own boxes), a penalty per tier, the arrow's distance from the tap, a slight preference for below and a centred arrow. Bubbles are 300 px wide at most (`--ax` sets the arrow), live in a `.lvl` layer of the day column (`aria-live="polite"`, *Happening now*) and scroll with the grid. **Following:** the now line is kept **a third of the way down** the visible grid (the top before the visible hours), on the 30-second tick (`liveTick`) and after every redraw (zoom too), within the scroll limits; it **never moves while a dialog, a menu or a held pointer** is open (`liveBusy`); **at midnight** it moves on to the next day (also onto a hidden weekend day); the now line is drawn even when *Show now line* is off. **A manual scroll** (one live view did not make, `liveTop`) **pauses** following, shows **Now**, and **comes back by itself a minute after the last manual scroll** (`LV_BACK`, `lvRet`, `liveBack`) **[U]**; *Now* does it at once. **Bottom pill** **[U]**: a larger **● Live View Mode** pill (`#lvPill`, *Modo vista en directo*) with a **pulsing red recording dot** (`lvp` animation, off under `prefers-reduced-motion`); the *N hidden* pill is never shown in this mode **[U]**. **Leaving: only** the pill, **Stop Live View** or **Esc** (not under a dialog or menu), always back to **the week** **[U]**. The sidebar can still be opened, hidden and used **[U]** (the grid redraws and stays live; print prints the day view without the cards). **Remembered per browser** (`prefs.live`): a reload opens straight into today's Live View — the one exception to "focus is not remembered". View state only. Tooltips explain each control; help tip 19.
- **R-GRID-10** **[C✓]** Layer order in a day column: phase backgrounds → background-activity bands (R-EVT-17) → hour lines (drawn *over* phases, **[U]**) → events → overlap stripes (in the day column, over the boxes' colours, under all event text) → nested boxes (R-NST-02) → now line.

## 3. Events
- **R-EVT-01** **[U]** Rounded boxes with a background colour, like Google Calendar. Created by dragging on empty space of a day (a plain click/short drag creates a 1-hour event) **[C✓]** or with the **+** toolbar button **[U]**. Can be removed, moved up/down within a day, moved to other days, resized, and may overlap other events.
- **R-EVT-02** **[U]** Fields: title (required), description (optional), an **owner** (optional, R-EVT-20), the default **persons involved** (multi-select of our people; a day can have its own list, R-EVT-21), colour, and **at least one schedule**; each repetition has its own times, the person who **performs** it (its *responsible person*: the owner by default) and timing (R-UI-07). Toggling a schedule shows/hides its events.
- **R-EVT-03** **[U]** **Event box layout (rows):** row 1 = responsible person's icon (only if there is one, just before the title, sized to the text) + title on the left, the **time range right-aligned**, then the status icons (repeat / ⚠ / lock, top-right, **[U]** unchanged); row 2 = `By: <responsible name>` (no icon, left) and, right-aligned on the same row, `With: <involved people with icons>`; **no description row — the description is never shown in the compact grid view (event boxes, print schedule, print day view); it appears only in the peek card, the agendas and the dialog [U]**. Person icons inside event boxes are small (10 px glyph on a white disc) **[U]**. Continuation pieces show `from Fri 22:00 · until 02:00` as their time.
- **R-EVT-04** **[U]** Status icons top-right of the box: the **activity type icon** (R-EVT-11), **repeat icon** (event has >1 repetition), **[C✓]** ⚠ (repetitions of this event overlap and clash, R-REP-05), lock icon (locked).
- **R-EVT-05** **[U]** **Clipping:** event boxes render the *By/With* row only if it fits completely (`fitBox`, measured after layout; otherwise it is dropped). When anything is hidden (that row dropped or the title ellipsised) the box shows a small **⋯** marker plus a faint bottom fade (`.clipped`). **[U]** **Peek card** (mouse hover ~0.35 s over an event, locked ones included — hit-tested at column level, up to 3 stacked overlapping events): title (colour chip, responsible icon), time, `By: …`, `With: …` (icons), full description, schedules, ⚠ and lock notes, then a gap and the UI-behaviour instruction lines (for repeating events: "Dragging changes all repetitions; hold Shift to change only this one."; the number of repetitions is deliberately not shown). The peek card replaced the native tooltip (events keep an `aria-label`); it is hover-only — on touch a tap opens the dialog, which shows everything.
- **R-EVT-06** **[U]** Dialog **Delete** is a single button: removes the whole event including all repetitions and closes the dialog (no confirmation, no "delete all repeats" wording).
- **R-EVT-07** **[U]** **Copy** lives in its own dialog (opened by the "Copy…" button of the event dialog, or by **right-click** on the grid **[C✓]**): choose destination schedule and colour (same colour / same hue brighter-or-darker / random / chosen). Default: tweak when the destination already contains the event, otherwise same colour **[U]**. A copy is an independent event (to share one event, tick several schedules) — the dialog says so **[C✓]**.
- **R-EVT-08** **[U]** Event opacity = highest opacity among its visible schedules.
- **R-EVT-09** **[U]** Overlapping events that are drawn on top of each other (see R-EVT-10 for which ones): the overlapped range is drawn as **diagonal stripes mixing the overlapping colours** (45°, 7 px bands, 85 % of the highest opacity among the overlapping events), within that lane only. **[C✓]** Same-colour overlaps get a lightened stripe so they stay visible.
- **R-EVT-10** **[U]** **Side by side vs on top:** stripes mean "possible conflict", side by side means "in parallel, fine". Two overlapping occurrences in a day column **clash** — drawn **on top of each other with stripes** — when they **share a person** (responsible or involved, in either role; people *on call* don't count, R-EVT-16) **[U]** or either has **no responsible person** (even with involved people: they are busy, and nobody else is assigned, so it concerns everyone) **[U]**; otherwise they are **parallel** and go **side by side**. **Repetitions of one event follow the same rule** **[U]**: being the same event is no reason to clash (it used to be), so two overlapping repetitions performed by people who share nobody go side by side without stripes or ⚠ (R-REP-05); one rule, `clash()`, serves the lanes and the ⚠. Decided per occurrence (each repetition has its own responsible person) and from visible occurrences only (people filter, hidden schedules). Layout (`laneLayout`): each group of time-overlapping occurrences splits the column into as many lanes as it needs (non-overlapping events keep the full width) **[U]**; lanes are ordered by the People list as shown (responsible person; reorderable, R-PPL-02; external people after ours, R-PPL-04), then start time. Each occurrence gets a **range of lanes** (R-EVT-13, R-EVT-18). Lanes are computed, never stored: dragging sideways within a day changes nothing. Click/drag/resize/peek/right-click hit-testing uses the pointer's x (`laneMap`, `inLane`, `fxAt`), so side-by-side events open/move directly without a chooser. **[C✓]** Settings → View *Show parallel events side by side* (`prefs.side`, default on; off = everything overlaps with stripes as before). When lanes get narrow, untick *Fit width*, raise the column width (R-GRID-07) and scroll sideways (the tooltip says so). Background activities of external people (R-EVT-17) are not boxes and take no part in this at all; nested activities (R-NST-01) are taken out before the layout too and drawn inside their host.

## 4. Repetitions
- **R-EVT-13** **[U]** **Spanning lanes:** an occurrence that clashes with two (or more) occurrences that are parallel to each other **spans their lanes** instead of merging them: the parallel ones stay side by side and the spanning one overlaps each **independently**, striped only inside that lane (stripes are computed per group and lane; identical neighbouring lane segments are joined). Rule: parallel + overlapping ⇒ lane ranges disjoint; clashing + overlapping ⇒ ranges share a lane. Algorithm: occurrences that are not spanners are bundled (transitive clashes) and packed into lanes; each spanner takes the range from the leftmost to the rightmost lane of what it clashes with; the result is validated. **Lanes may be reordered** (all orders of up to 6 lanes, tried in order of closeness to the People order, People order first) so that the occurrences a spanner clashes with become neighbours **[U]**. Settings → View, nested under *Show parallel events side by side*: **Keep lanes in the order of the People list** (`prefs.sideFix`, default off, disabled while side-by-side is off) **[U]**. When no order works (or with the fixed order, or >6 lanes, or >60 occurrences in one group) that group **falls back to merging** its clashing occurrences into shared lanes with stripes — a deliberately distinct "something is wrong here" signal **[U]**. Groups in which nothing is parallel are one lane without any search. Hit-testing uses the range (`laneMap` = `[first, last, lanes]`); `data-lane` is `l/n` or `l0-l1/n`.
- **R-EVT-18** **[U]** **Reaching its people's lanes:** an occurrence also spans the **own lanes of its people** (responsible or involved; people only on call don't count, R-EVT-16) where nothing parallel is in the way, even when it clashes with nothing there. Example found by the user: Luis works 09:00–12:00 and 13:00–17:00, has lunch 12:00–13:00 with Ioanna, who works 10:00–16:00. The lunch clashes only with Ioanna's work, so it used to sit in her lane alone; now it spans Luis's lane (free between his two work blocks) and hers, striped only where it overlaps her work. **[C✓]** A person's *own lanes* are the lanes holding bundles led by that person alone (a mixed bundle, like the lunch with Ioanna's work, belongs to nobody; this keeps Luis's work from reaching for the lunch's lane). Applied after the spanning step to every order tried (`join` in `laneLayout`): the lane-order search takes the first order where every occurrence reaches its people's lanes, otherwise the valid order where the most do (ties: closest to the People order). With *Keep lanes in the order of the People list* only that order is used. It never makes a layout invalid: an occurrence grows only where it meets no parallel occurrence. **An occurrence without a responsible person concerns everyone** (R-EVT-10), so it spans **every lane of its group** **[U]** — always possible, since it clashes with everything it overlaps. Example found by the user: Luis and Ioanna both work 13:00–17:00 side by side (Luis may finish 15 minutes early), and the school pickup 16:45–18:00 (no responsible person, Olivia involved) used to sit in Ioanna's lane only; now it spans both, striped over her work and covering Luis's flexible end (a core covers margins, R-EVT-15).
- **R-EVT-11** **[U]** **Activity type:** each event has **at most one** activity type (`type` = a type id, stored only when set), for the **whole event** (not per repetition) **[U]** — one type per event so a later per-person statistics view can put every minute in exactly one bucket. Dialog: an *Activity type* list (`#fTy`, `(none)` first, then the workspace's types; the chosen type's icon is shown beside it). The type's **icon is the first status icon** on every box (R-EVT-04); peek card, agenda and `aria-label` name it (icon in the type colour). Boxes keep the **event's own colour** — the type colour is for statistics only **[U]**. A type with the **soft look** (default: Free time) draws its events as free time was drawn before **[U]**: a soft tint of the event colour (`color-mix` with `--card`, follows light/dark, prints light), a solid 4 px colour edge on the left, dark text without shadow (`.ev.soft`). Otherwise typed events behave like any event — **the overlap rules (R-EVT-09/10) do not change [U]**. This **replaced** the earlier *Free time* checkbox / `free:true` flag outright (no migration; unreleased app) **[U]**. Phases never carry a type **[U]**.
- **R-EVT-12** **[U]** **Flexible time** (name chosen over "tentative", which calendars use for "maybe/unconfirmed" **[U]**): the activity happens *around* the given times but may not take the whole slot. Stored **per repetition** (`slot.flex:true`, only when set) **[U]**. Dialog: one of the three choices of each time's own **Timing** list (R-EVT-15, R-UI-07). Drawn with a **2 px dashed border** **[U]** (`--dash`: light on dark colours, dark on light ones via `ink()`, a darker shade of the colour on soft-look boxes). Peek card, agenda and `aria-label` say *Flexible time (around these times)*. Independent of the activity type (it's about *when*, not *what*). Phases never have it. **Overlap rules do not change [U]**; drags keep the marks.
- **R-EVT-15** **[U]** **Flexible start/end** (*Inicio/fin flexible*): a task that may start a bit late and/or finish a bit early (e.g. work 09:00–17:00, fine to start any time until 09:30 and to wrap up from 16:45).
  - **Model [U]:** per repetition, `slot.fs` = flexible minutes *after the start*, `slot.fe` = flexible minutes *before the end* (15-min steps, stored only when > 0). The slot's `start`/`end` stay the **outer** times, so moving, past-midnight pieces and hidden-hour counting are unchanged. **Core** = `start+fs` … `end−fe` (`coreOf`, per piece `coreIn`); the parts outside it are the **margins**. **[C✓]** The core stays ≥ 15 min (`fitMg`: shrinks the end margin first, then the start margin); `parseData` snaps and clamps; the dialog refuses a save that would break it, naming the day (`errCore`). Phases never have margins.
  - **Both kinds of flexible time are kept [U]**, as one per-repetition choice: each time's **Timing** list (`.tsel`, *Horas* in Spanish — not *Horario*, which is the word for schedule): **Fixed** / **Flexible start/end** / **Around these times** (R-EVT-12); mutually exclusive (`parseData` drops `fs`/`fe` on a `flex` slot). Choosing *Flexible start/end* shows, on a line of its own under that day (`.dsub`), *May start up to [list] late, and finish up to [list] early* (0, 15, 30, 45 min, 1 h, 1 h 15, 1 h 30, 2, 2½, 3, 4 h; 15/15 by default); a margin of 0 is not stored, both 0 = fixed. There is **no event-level timing** (it used to be a *Timing* switch that only set every day, with a per-day toggle and popover — removed as an event-level look-alike) **[U]**; the day's ⧉ button copies its timing to the other days.
  - **Drawing [U]:** the core is a normal solid box; the margins (`.mg.t` / `.mg.b`, children of the day column in the event's lane) continue it above/below with a **2 px dashed border in the event colour**, no border towards the core, and a **translucent tint** (30 %, 14 % for soft-look types); only the outer corners are rounded. **[C✓]** The **text sits in the core box** (not at the top of the whole window as first planned): the core must be drawn above every margin, so the text has to live in the core. A piece that is **all margin** (e.g. the part after midnight of an event whose end margin covers it) is drawn as a dashed box with the text (`.ev.mgo`). The time shown is the outer range (`09:00–17:00`); peek card, agenda and `aria-label` add *Start between 09:00 and 09:30 · Finish between 16:45 and 17:00* (`edgeNote`). The resize handle sits at the outer end; dragging a margin moves the event.
  - **Overlaps — only cores count [U]:** stripes (R-EVT-09) and the repetition ⚠ (R-REP-05, `overlapSet` via `ivs`) appear only where **core overlaps core**. **Side-by-side lanes use core times too [U]:** occurrences that touch only through margins are not in the same lane group, so both keep the full column width (the alternative — 15 flexible minutes putting a parallel event side by side, at half width, for its whole length — was rejected). Margins follow their event's lane.
  - **Drawing order [U]:** every margin is inserted **before every core box** in the day column (after the hour lines), so a core always covers the margins of other events — **hidden entirely, dashed outline included**. Margin on margin: the tints mix, each keeps its dashed edges, the later-starting one on top (fallback if it ever looks messy: show only the top margin's tint there). **Hit-testing** (`piecesAt`): where a core is under the pointer, only cores count — a core over a margin opens/drags/peeks the core's event directly; margins alone behave like any overlap (chooser). Known side effect: resize handles stay above every box (bug 6 in §14), so the last ~9 minutes of an event's window still grab its handle even where another core covers its end margin.
  - **Statistics [U]:** margins count as **planned** time and are added to the hatched *of which flexible* part. **[C✓]** Double-booked time: a core beats a margin (the core's event gets that time); margin vs margin is split evenly; the *Overlapping* line and its places count only core on core.
  - **Dragging [C✓]:** moving keeps the margins; resizing (also "all repetitions" and *Only this day*) keeps their lengths, shrinking them if the core would drop below 15 min. Dragging the core's own edges may come later.
- **R-EVT-16** **[U]** **Involved people only on call** (`event.oncall:true`, only when set; per event, like `involved`): the involved people are *available, not busy* — e.g. Ann at hand to answer the cleaner's questions. Dialog: checkbox **Involved people are only on call** in *How it fits in* (`#fOnCall`, tooltip explains; shown while somebody is involved, by default or on some day, R-EVT-21). Effects: in the **clash rule** (R-EVT-10, `pplOf`) only the responsible person counts as shared, never the involved ones (*no responsible person* still clashes); in **statistics** the involvement doesn't count, even with *Include time as involved person* **[U]**; box row 2, peek card, agenda and `aria-label` say **On call:** (*De guardia:*) instead of *With:*. The people filter (`slotVisible`) is unchanged.
- **R-EVT-17** **[U]** **Background activities** (`isBg`): an event marked **In the background** (R-EVT-19) is drawn as a **strip** (`.bgs`, 14 px, event colour) instead of a box **[U]** — the cleaner "just happening" without bothering anyone, or screen-free time. Strips come **only from the mark**: activities of external people (R-PPL-03) are ordinary boxes unless marked; the automatic rule that made them strips (external responsible person, nobody involved or only on call) was removed because it overlapped with the mark **[U]**, and saved data from before is upgraded (`MIG[3]`, R-DATA-08). Strips sit at the **right edge** of the day column; **[C✓]** a column with strips reserves a gutter (`--gut` on `.day`, `gutMap`; 16 px per strip sub-lane) that boxes, margins, stripes and handles stop before, so boxes lose a few pixels rather than half their width; overlapping strips are packed side by side in the gutter (`data-strip="k/n"`). Strips **never take part in lanes or stripes** and never make anything clash (excluded from `laneLayout` before it runs). **Looks like a lip [U]:** the first strip is flush with the column's right edge, right corners rounded and left corners straight (a mirrored phase lip; a piece cut at midnight keeps only its outer right corner rounded), and it shows the **title vertically, reading top-to-bottom** (`writing-mode:vertical-rl`, no rotation; 10 px bold, ellipsis, `textContent`), in `ink()` colour **[U]**. Phase lips deliberately keep reading bottom-to-top **[U]**. The rest (person, times) is in the peek card and `aria-label`; the ⚠ of overlapping repetitions only in the peek card. Flexible start/end shows as a lighter part (gradient) and the title starts where the solid core starts; flexible time is a dashed strip; dashed and all-margin strips use the page text colour. **Background band [U]:** each strip also tints its column for its time window (`.bgb`, a child of `.day` inserted before the hour lines `.gl`, so it lies under hour lines, margins, boxes and stripes): the **full event colour next to its strip** (so it joins the strip without a visible step **[U]**) **fading to transparent at the column's left edge** (`linear-gradient(to left, …)`), from `left:0` up to its own strip (`right` = the strip's offset + 14 px, so with several strips each band reaches its own one and runs under the nearer ones); schedule opacity applies; overlapping bands mix; flexible start/end margins are fainter (vertical `mask-image`), flexible-time and all-margin pieces give a half-strength band; dimmed in Phases mode. **Only the lip is interactive [U]:** the band has `pointer-events:none`, so presses, drags, hovers and right-clicks on it act on whatever is beneath (a box, or empty space → create an event); hit-testing never finds a strip outside the gutter. Interaction like any event (hover peek, tap/click opens, drag moves, bottom handle resizes, locked = click-through, inert in Phases mode); hit-testing by x: `laneMap` holds `['s', from, to]` in px from the right edge (sub-lane k owns `[16k, 16k+16)`, so strips and boxes meet without a gap) and `inLane` (which now gets the day) keeps boxes out of the gutter, using the column width `fxAt` measured (`fxW`). An unmarked event is a **normal box** with the normal rules whoever leads it (a babysitter with Lucía clashes through Lucía).
- **R-EVT-19** **[U]** **In the background** (`event.bg:true`, only when set; per event; *En segundo plano*; first called *Doesn't keep anyone busy*, renamed because it also covers the cleaner, who is busy **[U]**): for things that happen **without keeping the household busy** — the cleaner at work, or *screen-free time* for Olivia 18:00–20:00 while she still does homework, has dinner and a bath (this was the parked *non-obstructive tasks* idea; chosen over a separate kind of item "rules/conditions" and over phases with people **[U]**). A marked event is a **background strip** (R-EVT-17; it is now the only way to get one **[U]**) **whoever leads it** — one of our people, an external one, or nobody (= the whole family) — with its people kept as usual **[U]**: no lanes, stripes or clashes, never nested and never a host (R-NST-01); the people filter applies as to any event. **Purely informational** (no warnings about activities during it) **[U]**. **Left out of the statistics entirely** (for every person, also as involved time) **[U]**. Dialog: a checkbox in the *When* section under the nesting one, **In the background (doesn't keep the household busy)** (*En segundo plano (no ocupa a los de casa)*, `#fBg`, tooltip with screen-free time and the cleaner as examples; strips are *tiras* in Spanish, never *franjas*, which are phases); while it is ticked the nesting checkbox is disabled (`updBg`; the tooltip says why). Hover card, agenda and the strip's `aria-label` add *In the background*; the strip's label says *By:* only when somebody is responsible, *(external)* only for external people, and *With:* unless the involved people are on call. A help tip (help18) describes it; help15 and the *External* menu tooltip point to it.
- **R-EVT-20** **[U]** **Owner of an event** (Fair Play's *CPE*: conceive, plan, execute — the partner who holds the whole task, even when someone else does it on a given day): `event.owner` (a person id, optional **[U]**; only **our people** can own an event **[U]** — an owner who later becomes external is kept and shown as such). The **responsible person of an occurrence** (`slot.person`) is whoever **performs** it; it defaults to the owner: a day marked **Owner** (`slot.fo:true`) **follows the owner** — choosing another owner moves all of them, while a **stand-in** (a named person) stays **[U]**; `slot.person` always holds the effective performer (`parseData` and every owner change keep `fo` days at `owner || ''`), so **clashes, lanes, stripes, statistics and the people filter are unchanged** and keep using the performer **[U]**. Without an owner, *Owner* days are performed by nobody until one is chosen. Deleting the owner leaves the event unowned (its *Owner* days keep following); insert and schedule transfers map the owner through the people mapping. Hover card, agenda and `aria-label` add **Owner: Ann** (*Titular:*). **Upgrade (format 5, `MIG[4]`):** each event gets as owner its most frequent performer among our people (ties: the earliest repetition), and the days they perform become *Owner* days; events performed only by external people or by nobody stay unowned.
- **R-EVT-21** **[U]** **Involved people per day:** `event.involved` is the **default** list and a day can have its **own list** (`slot.inv`, stored only when it differs from the default; `[]` = nobody that day) **[U]**. The effective list (`invOf(e,s)`) is what clashes (`pplOf`), nesting hosts, the people filter (`slotVisible`), statistics and every label use. Edited with the day's **With** button (R-UI-07); deleting a person removes them from the days' lists; insert and transfers map them. *Only on call* (R-EVT-16) stays event-wide and applies to whichever list is in effect.
- **R-REP-01** **[U]** An event can repeat on chosen days of the week. Each day has **its own times** (there are no event-level *general times* any more **[U]**; a newly ticked day starts with the times of the nearest ticked day above it, else below, else 09:00–10:00, performed by the owner, with the default involved people, fixed), its **own performer** (R-EVT-20) and its own involved people if it differs (R-EVT-21); all share colour/title/etc. Repetitions can be removed or retimed individually (dialog), and deleting the event deletes all.
- **R-REP-02** **[U]** **One day table, no modes** **[U]**: the dialog lists Mon–Sun; a ticked day's first time sits in its row, and its **+** (*Add another time on Monday*) adds **further times on that day** as lines below it (`.dr.dx`; starting where the day's last time ends — or with it after 23:00 —, an hour long, performed by the owner, With *Default*, fixed), each with its own start, end, performer, With, timing and a **✕**. The day's **⧉** makes **every other ticked day like this one** — all its times, performers, With lists and timing, adding or removing their further times **[U]**. An event with several times on a day opens with those lines (in time order); unticking a day greys out all its lines (kept until saving, dropped on save). Moving a time to another day is done by dragging it on the grid. This **replaced the Quick and Advanced tabs** (Quick: one time per day; Advanced: a flat list of blocks with a day list, which locked Quick once a day had two) **[U]**.
- **R-REP-03** **[U]** Events may **run past midnight**: end up to `MAXEND = 2880` (midnight at the end of the *next* day). Overflow stops at the next day; **Sunday wraps into Monday**. Drawn as joined pieces with flat edges; labels `22:00–02:00 (Next day)` / `from Fri 22:00 · until 02:00`. Only the last piece has the resize handle.
- **R-REP-04** **[U]** End-time select labels: `…23:45`, `00:00 (Next day)`, `00:15 (Next day)` … `23:45 (Next day)`, `00:00 (Day after next)`; entries ≤ start are disabled. Compact displays (boxes, agenda, tooltips): plain midnight → `00:00`; any later end → `(Next day)` suffix, including the end of the next day (`00:00 (Next day)`). *Known inconsistency between select and compact notation — alignment proposed, not done* **[P]**.
- **R-REP-05** **[U]** **Overlapping repetitions are allowed but warned about** — **only when they clash** by the people rule of R-EVT-10 (a shared person, not on call, or either without a responsible person; phases have no people, so theirs always clash) **[U]**; `overlapSet(e, slots)`, and the dialog checks the values as they would be saved (performers, owner, With lists, *only on call*), updating on every change: ⚠ on the affected dialog rows + summary line; ⚠ icons on the grid pieces; a toast when a drag/resize *creates* new overlaps (with Undo).
- **R-REP-06** **[U]** **Drag/resize of a repeating event changes ALL repetitions by default** (live preview), **Shift** (also mid-drag) changes only the grabbed one. After an "all" drop a toast offers **Only this day** and **Undo**. Moves shift every repetition by the same minutes and days (mod 7); resizes change every end by the same amount; **minimum duration is 15 minutes — a repetition is never removed by resizing**. Dragging a resize handle into the next day's column extends past midnight. An event with at most one time per day blocks moving a single repetition onto a day that already has one; once a day has two times it is allowed (`isAdv`).
- **R-REP-07** **[U]** No confirmation dialog for repeat drags (an earlier confirm dialog was rejected).

## 4b. Nested activities (small tasks done during another activity)
- **R-NST-01** **[U]** Some small tasks are done **along the way, during another activity of the same person**: e.g. *Collect milk* (15 min, three mornings a week, on the days the milk is delivered) is done at the end of the school run, but on Saturday, with no school run, it stands alone. It is a **real event** (own time, person, type, repetitions) with the per-event mark **`event.nest:true`** (stored only when set, like `oncall`; dialog: R-NST-05). This **replaced free-text "extras" on one occurrence**, which were built and withdrawn because the task needs its own time and person and must be able to stand alone **[U]**. **Rule** (`nestPick`, one helper for grid, agenda, drag and statistics): an occurrence piece of a marked event is **nested** when it has a responsible person P and its **core** (R-EVT-15) lies **entirely** within the windows (start…end, flexible margins included) of other occurrences that are **activities of P** — P responsible or involved, *not* on call (`pplOf`) — **any activity of that person**, not a chosen event **[U]**; several back to back may cover it together **[U]**. Hosts are never marked events themselves (no chains) and never background strips; strips themselves never nest. Its **host** is the occurrence covering the core's start. **Partly covered = not nested**: it is an ordinary occurrence that clashes as usual, so a slipped task stands out **[C✓]**. Hosts that are not drawn (hidden schedule, people filter) don't count on the grid. Nesting is **computed, never stored** (no link data).
- **R-NST-02** **[U]** **Drawn as an inset box** inside its host **at its own time and duration** **[U]**: a normal event box (rows, flags, clipping, 14 px minimum height like every box) with class `nest`, horizontally within the host's lane range **indented 14 px on the left** (`insetPos`, `NI`; also in a one-lane column), with a ring in the card colour, above the host's text and the stripes (`z-index:5`, drawn after the other boxes). Nested pieces are **taken out before `laneLayout`**: they take no lane, cause no stripes and never clash; the host keeps its lane. Spanning several hosts, it follows the lanes of the first one ("try it and see" **[U]**). **Hit-testing:** `laneMap` holds `['n', l, l1, n]`; `inLane` excludes the indent; `piecesAt` and `handlesAt` give a nested box priority over what is beneath (`nestFirst`), so it opens/drags/peeks directly and the host is reached beside it. Peek card, `aria-label` and day agenda say *During: School run* (*Durante:*); the host's peek card lists *Also during this: Collect milk 08:15–08:30*.
- **R-NST-03** **[C✓]** **Moving a host carries what is nested in it** (`nestCarry`/`carryMove`): at the start of a move every nested occurrence hosted by a repetition of the grabbed event is recorded and follows **the shift of its own host repetition** (so an all-repetitions move carries all of them, Shift carries only the grabbed day's, and the one standing alone on Saturday stays); an event with at most one time per day keeps it that way (a carried one that would land on a used day stays); locked ones never move. One undo step; *Only this day* puts the others back. Resizing a host carries nothing; dragging the nested one is a normal drag.
- **R-NST-04** **[U]** **Statistics:** the shared minutes **go to the nested activity** and the host loses them (so chores show up), computed from the visible schedules regardless of the people filter and the *involved* toggle; that time is **not** *Overlapping* (only two nested ones at the same time, or ordinary core on core, are).
- **R-NST-05** **[U]** **Dialog:** a checkbox in the *When* section under Timing, **Can be done during the person's other activities** (*Se puede hacer durante otras actividades de la persona*, `#fNest`), with a tooltip explaining the drawing, the statistics and the carrying; events only. A help tip (help17) describes it.

## 5. Choosing among overlapping things (click vs drag)
- **R-SEL-01** **[U]** **Click** (open dialog): if everything under the pointer belongs to one event (even several overlapping repetitions) the dialog opens directly; if different events overlap, a small list shows each event once (repetitions grouped). "Under the pointer" means the same time *and* the same lane: events side by side (R-EVT-10) never trigger a chooser for each other.
- **R-SEL-02** **[U]** **Drag** (move or resize): if more than one event *or repetition* could be meant (bodies for moves; bottom ~9 min for resizes) a chooser lists each repetition separately (with its day/times). **[C✓]** The pick becomes the **selection** (`selK={id,i}`): outlined and raised above neighbours; the next drag that starts where it is a candidate acts on it directly. Esc, a click on empty space, or undo/redo clears it. (Two-step by design: you cannot choose while the button is held.)
- **R-SEL-03** **[C✓]** Right-click on a day column lists events/phases under the pointer → Copy dialog.
- **R-TOUCH-01** **[U]** **Touch (Google-Calendar style, mouse behaviour unchanged):** dragging scrolls natively (`touch-action:pan-x pan-y` on day columns/lanes); a **tap** opens an event (or the chooser if several events overlap); a **long-press (0.4 s, vibration tick)** on empty space starts creating an event, on an event starts moving it, on its bottom handle starts resizing (handle hit area is 16 px on coarse pointers). `press()` implements it; `touchmove` is `preventDefault`-ed only while a long-press drag is active. The native long-press context menu is suppressed, so **right-click Copy has no touch equivalent** (Copy… in the event dialog works; locked events can't be copied on touch) **[P]**.

## 7. People
- **R-PPL-01** **[U]** A People list "created in the same fashion as schedules": name, colour, icon, eye (show/hide). **Visibility rule (`slotVisible`, on the occurrence's performer and its effective involved people, R-EVT-20/21) — viewing a person's calendar:** an occurrence with **no responsible person is always shown** (unless its schedule is hidden), whatever its involved people; otherwise it is shown when its responsible person is shown **or** any involved person is shown. So viewing a single person shows everything except occurrences led by someone else in which that person is not involved. (With nobody shown, only occurrences without a responsible person remain.) Rule is per repetition, since each repetition has its own responsible person. Deleting a person removes them from all events. Person ⋯ menu: Colour…, Statistics… (not for external people), External (not one of us), Delete.
- **R-PPL-03** **[U]** **External people** (`person.external:true`, only when set): someone from outside the household — a cleaner, a gardener, a babysitter — who does activities but isn't "one of us" **[U]**. Toggled in the person ⋯ menu (*External (not one of us)*, tick + explanatory tooltip, undoable data); the row shows a small external-link marker (`.extb`, labelled). Their rows are listed in the **External** sub-group of the People section (R-PPL-04). They stay normal people otherwise: own eye (visibility rule unchanged), the responsible list (adds *(external)*), lane order (after ours). **They are never offered as involved people** (the dialog's *With* chips list `ourPeople()` only) **[U]**. **Left out of the statistics** (person picker, *Everyone*, its table; `ourPeople()`); only external people → the "add people first" toast. Their activities are ordinary boxes; tick *In the background* (R-EVT-19) to draw one as a strip (R-EVT-17). `parseData` keeps the flag only when `true`; it travels with files, links, insert, transfer (a person created in the target keeps it) and anonymised exports.
- **R-PPL-02** **[U]** **Reordering people:** each person row starts with a **grip** (six dots, shown on hover; always faintly visible on touch screens) — drag it up/down (drop line shows the target) or focus it and use the **arrow keys**. The order is data (undoable, unsaved) and sets the order of side-by-side lanes (R-EVT-10/13) — the order *as shown*, i.e. our people first, external people after them (`pIdx` in `laneLayout`). Other lists are not reorderable yet.
- **R-PPL-04** **[U]** **External people are folded away** (they rarely matter): the People section lists our people first; external ones (R-PPL-03) follow under a collapsible sub-header **External (N)** (`.subh`, chevron, `aria-expanded`, ⓘ tip; when folded and some of them are hidden by their eye it adds *· N hidden*), **folded by default** (per-browser pref `secExt`; anything but `false` = folded) **[U]**. Unfolded, their rows (`.extg`) are the usual rows (grip, eye, icon, name, external marker, ⋯). No sub-header when there are no external people. The grip reorders **within its group** only (`gripFor(row, list, item, group)`): the person lands just before/after the group neighbour it passes, so the data positions of the other group are untouched **[C✓]**. Marking someone external just moves their row; the data order stays.

## 8. Phases and rhythms (background day-structure)
- **R-PHS-01** **[U]** A **rhythm** = the regular cadence of a home/workplace over a week (e.g. "Normal rhythm", "Holiday rhythm"); a **phase** = a named part of the day (Sleep time, Lunch time…). (Originally "periods"/"period sets"; renamed by the user's choice, Spanish: *franjas* / *ritmos*.)
- **R-PHS-02** **[U]** Rhythms behave a bit like schedules but are separate entities; a rhythm can be hidden but **only one rhythm can be shown at a time**. Phases are **always in the background**, drawn as a colour band behind events with the hour lines/borders over it. **One opacity control for all rhythms** (slider in the Rhythms section); the lips are always fully opaque. Rhythm visibility and the opacity are view state (§10).
- **R-PHS-03** **[U]** Phase fields: name, description (optional), colour, ≥1 rhythm; **no people**. Repetitions stay within one day; same day table as events (R-REP-02); a phase can belong to several rhythms and be copied to another rhythm (same Copy dialog).
- **R-PHS-04** **[U]** **Lips:** a vertical-text tab in a lane **outside, to the left of** each day column, its right edge flush with the column's left border. Hover tooltip: name, day range (e.g. `Mon–Fri`), times, description. **Grouping:** if the previous *displayed* column has the same phase with identical start/end, no lip is drawn there; **the lane still shows the phase colour as a translucent band (same opacity setting)** so the colour is continuous across the group. Different timings → each gets a lip. The lane exists (18 px) only while a rhythm is visible.
- **R-PHS-05** **[U]** Phases are never counted as hidden by the hidden-weekend/early-hours settings, and are drawn through hidden-hour clipping like anything else.
- **R-PHS-06** **[U]** **Edit mode** switch (sidebar: *Events | Phases*): in Phases mode events are inert and dimmed (35 % opacity, desaturated) and phase repetitions are interactive; in Events mode phases are pure background (lips still show tooltips). Editing one kind can never affect the other. **[C✓]** In Phases mode phase boxes get **dashed borders in their colour**, an inline label (`name · times`), a resize handle, the lip becomes a drag handle, and the grid gets an accent-coloured inset outline as a mode cue. Drag, resize, Shift-single, toast, choosers and right-click Copy work exactly as for events.
- **R-PHS-07** **[U]** **Rhythm agenda** (agenda icon on the rhythm row): phases sorted by earliest start, then grouped into runs of consecutive days with identical times, scanning Monday→Sunday with **no Sunday→Monday wrap** (e.g. `Monday to Thursday 12:00–13:00`, `Friday 13:00–14:00`, `Saturday to Sunday 12:00–13:00`). ## 10. Persistence and data
- **R-DATA-01** **[U]** **Workspaces:** several named, fully independent data sets (schedules, people, activity types, events, rhythms, phases) live in memory at once; the sidebar has a **workspace switcher** under the title (menu: switch, *New workspace…*, *Rename current…*, *Duplicate current*, *Delete current…*; • marks unsaved ones; the last workspace can't be deleted). `S` always points to the current workspace's data; `WS=[{id,name,data,lb,lf,undo,redo}]`, `curId`; `syncWs()` writes the live `S`/history back into the record before switching/saving; **undo/redo history, selection and dirty state are per workspace**. A *new* workspace starts from `defaultData()` (Routine schedule + default activity types + Normal rhythm); *Duplicate* copies the data and counts as unsaved.
- **R-DATA-02** **[U]** **Save…** asks the target (browser memory / JSON file — encrypted by default, unencrypted on request (R-SHARE-07) / password-protected shareable link). **Files and links always hold exactly one workspace (the current one) [U]**; only **browser memory** asks, when there is more than one workspace, **which to save: only the current one or all** (browser memory itself stays unencrypted — locking it with a passphrase is deliberately postponed [U]). Browser memory (`localStorage` key `weekly-schedules-workspaces`, `{version:1,current,workspaces:[{id,name,…data}]}`): *current only* updates/inserts just that workspace's entry (other stored entries stay as last saved); *all* rewrites the whole store (deleted workspaces disappear). The (decrypted) content of a file/link is one workspace record `{version:1,id,name,schedules,people,types,events,rhythms,phases,phaseOpacity}` (`buildFile`, `parseWorkspace`).
- **R-DATA-03** **[U]** The app **auto-loads all workspaces from browser memory** at startup. **Load → Browser memory** reverts the *current* workspace to its saved copy (undoable). **Load → JSON file** and **opening a shareable link** never overwrite anything silently: both go through one **import dialog** (`openImport`) for the single workspace they contain, with exactly three options: **Import as a new workspace** (default; name made unique; keeps the file's id when free), **Insert into the current workspace** (its schedules, people, rhythms and phases arrive as *new* items with new ids; name clashes get "(2)"; inserted rhythms are hidden unless none was visible) or **Replace an existing workspace** — a single option that opens a picker listing *all* workspaces (best candidates first) with flags for the *active* one, the one with the *same id* and the ones with the *same name* (`pickReplace`), followed by a **confirmation naming the workspace that will be replaced** (`confirmReplace`). There is deliberately no separate "replace current" or "replace matching" option. After importing or replacing, the app switches to that workspace. **Nothing is ever merged** (no occurrence/event merging, no conflict resolution) **[U]**. Replace/insert are undoable in the affected workspace; imported-from-file workspaces count as saved (file), imported-from-link ones as unsaved. A first-time visitor with no browser memory and an untouched default workspace opening a link adopts it directly (`adoptWs`).
- **R-DATA-04** **[U]** **Copy/move between workspaces:** schedule and rhythm rows have *Copy or move to workspace…* (`openTransfer`): a **schedule** goes with all its events (attached only to the new schedule); a **rhythm** goes with all its phases; **individual phases cannot be copied or moved to another workspace [U] — only whole rhythms (with their phases)**; the Copy dialog for a phase only offers rhythms of the current workspace. For schedules, every person referenced by the events (responsible per repetition, involved) is listed in a **people mapping dialog** (`askPeople`): *create that person in the target*, *use an existing target person* (default: same name, case-insensitive; otherwise create), or *leave blank* (no responsible person / not involved). Copies get unique names in the target; both workspaces get an undo step; *move* removes the item from the source afterwards (schedule: events only in it are deleted; phase/rhythm likewise).
- **R-DATA-05** **[U]** **Clear memory** (confirmation) deletes the whole store (all workspaces) **and restarts the app** with one default workspace. **Restart** discards unsaved changes in all workspaces and reloads browser memory. `beforeunload` warns when *any* workspace has unsaved changes; a workspace is dirty when its data differs from both its last browser save and its last file save; the sidebar title shows • when any is dirty.
- **R-SHARE-01** **[U]** **Protected links and files** (reason: the data may describe vulnerable people such as children or the elderly): **links always require a password — there is no unencrypted link [U]**; JSON files are encrypted by default and only unencrypted when the user explicitly chooses so (R-SHARE-07). Save… → *JSON file* / *Shareable link* open one dialog (`openProtect`) with the options and the password field. Without `crypto.subtle` (old browsers/insecure contexts) links and opening encrypted files are refused with an explanation — never a plain fallback; the file dialog then only offers *Unencrypted* (with its warning, still a deliberate click on Save file).
- **R-SHARE-02** **[U]** *Leave out personal details* checkbox (unticked by default): people become "Person 1", "Person 2"… and event/phase descriptions are removed — `anonymised()`; titles and schedule/rhythm/workspace names are kept and the dialog says so; an anonymised export is **not** treated as a backup, i.e. it doesn't mark the workspace as saved to file.
- **R-SHARE-03** The password field is pre-filled with a generated password (`genPassword`: **25 random characters in 5 groups of 5**, unambiguous alphabet without 0/O/1/l/I, unbiased `crypto.getRandomValues`, ~145 bits) that can be regenerated or replaced; any password must be **at least 20 characters** (trimmed). The dialog tells the user to give the password to the other person by a *different route* than the link/file; the result dialog has *Copy* buttons for link and password.
- **R-SHARE-04** Crypto (`seal`/`unseal`, Web Crypto, no libraries): JSON → raw-deflate (if `CompressionStream` exists; flagged inside) → **AES-256-GCM** with a key from **PBKDF2-SHA256, 600,000 iterations**, random 16-byte salt and 12-byte IV per export; blob = `[1][iterations u32][salt][iv][ciphertext+tag]` with the header authenticated; decryption refuses iteration counts outside 100k–2M (crafted-file DoS), wrong passwords and altered data fail cleanly, and the decompressed size is capped at 2 MB.
- **R-SHARE-05** **Links:** `<app url>#data=e1.<base64url blob>` — in the URL fragment, which is never sent to web servers and not fetched by link previews; the result dialog shows the link and the password, the length (warning above 8,000 characters) and a `file://` note. **Opening:** `askPassword` (masked, show toggle, retry on wrong password); links are only understood in the `e1.` form (`e2.` and up: R-DATA-09) and re-checked on `hashchange`; the fragment is removed from the address bar after success or cancel. After decryption the content goes through the normal import dialog (or is adopted by a pristine first-time visitor). Invalid/too-large links show a toast and change nothing.
- **R-SHARE-06** **Files:** `{format:'weekly-schedules-encrypted',version:1,data:<base64url blob>}` named `weekly-schedules-<date>-encrypted.json` (the name deliberately doesn't reveal the workspace). Opening a file asks for the password (retry on mistakes); encrypted files and *plain* hand-written JSON files can both be imported (`weekly-schedules-encrypted` container detected by `format`). The dialog title is *Save JSON file*.
- **R-SHARE-07** **[U]** **Unencrypted JSON files (files only, never links [U]):** the JSON-file dialog has a switch **Encrypted (recommended)** (default, every time — the choice is never remembered) | **Unencrypted**. Unencrypted hides the password field and shows a warning box (`plainWarn`): anyone who gets the file can read everything, including plans of possibly vulnerable people (forwarded email, shared/cloud folder, lost USB stick, shared computer); use it as a private backup and prefer encryption or *Leave out personal details* when sending it. The file is the readable workspace record (`buildFile`, the same shape plain imports accept) named `weekly-schedules-<date>.json` (no `-encrypted`); it counts as a backup (marks the workspace saved to file) unless anonymised; it opens without a password through the import dialog. `saveFile(null, anon)` = unencrypted.
- **R-DATA-06** **[U]** **View settings are per browser, not in the save file** (`prefs`, key `weekly-schedules-prefs`): `showEarly`, `clock12`, `hideWeekend`, `side`, `sideFix`, `theme` (`auto`|`light`|`dark`), `rowH`, `colW`, `fitW`, `fitH`, `txt` (R-GRID-07; `fillW` and `fit` are retired, never read again), `live` (R-GRID-12), sidebar width/collapsed, section collapse flags (`secSch`, `secPpl`, `secTyp`, `secRh`, `secZoom`, and `secExt` for the External people sub-group, folded unless `false`). Data and view state are separated; *within* the file, `schedules[].visible/opacity`, `people[].visible`, `rhythms[].visible` and `phaseOpacity` are view state (saved, but ignored by `dataKey()` and preserved across undo).
- **Workspace data shape** (used inside the browser store, in files and in links):
```
schedules [{id,name,color,opacity,locked,visible}]
people    [{id,name,color,visible,external?}]   (external: true or absent)
types     [{id,name,color,icon,soft?}]   (icon: a TICONS key; soft: true or absent; colour for statistics only)
events    [{id,title,desc,color,type?,owner?,oncall?,nest?,bg?,schedules:[id],involved:[personId],slots:[{day,start,end,person,fo?,inv?,flex?,fs?,fe?}]}]   (owner: a person id or absent, R-EVT-20; fo: true when the day follows the owner (person = owner); inv: the day's own involved people, absent = the event's list, R-EVT-21; type: a type id or absent; oncall: true or absent; nest: true or absent, R-NST-01; bg: true or absent, R-EVT-19; flex: true or absent; fs/fe: flexible minutes after the start / before the end, > 0 or absent, never with flex)
```

**R-DATA-07** `day` 0 = Monday; times in minutes on a 15-min grid; event `start` 0–1425, `end` ≤ 2880; phase `end` ≤ 1440. `parseData()` is the single place that validates/sanitises input (clamps ranges, hex colours only, string length caps, drops events/phases without repetitions). It works on the **current** format only; older formats are upgraded before it (R-DATA-08). Development formats from before the launch are not supported (no legacy keys or shapes). Callers assign `S` themselves.
- **R-DATA-08** **[U]** **Backwards compatibility from the launch on:** everything saved by any released version must keep loading with the same meaning. **One version number** for the data format, `FMT` (now **5**: version 1 was frozen at launch, 2 added `event.nest`, 3 added `event.bg`, 4 made strips come only from `event.bg`, 5 added `event.owner`, `slot.fo` and `slot.inv`; `MIG[1]` and `MIG[2]` change nothing because older data has none of the new marks; `MIG[3]` marks `bg` on every event whose repetitions are all led by external people with nobody involved or only people on call, i.e. the strips of the old rule — events that were partly strips become boxes; `MIG[4]` guesses an owner, R-EVT-20): the version of a workspace record in files and links, and of the browser store (whose entries carry no version of their own). **[U]** It goes up on **any** change to what is stored, even an added optional field, because an older app drops fields it doesn't know and would lose them on the next save. **Upgrading:** `migrate(record, version)` runs before `parseData` on every input (file, link, each workspace of the browser store at startup, *Load → Browser memory*): the steps `MIG[n]` (raw version-n JSON → n+1) run one after another, so `parseData` only ever sees the current format; steps are never deleted. A missing version counts as 1 (hand-written files), a numeric string is accepted, anything else (0, negative, fractional, text) is *not a valid save file*. Old browser memory is upgraded in memory only and rewritten in the current format when the user saves (saving only the current workspace also upgrades the other stored entries). **Settings** (`prefs`) have no version (none = 1): a key never changes its meaning, and unknown or missing values fall back to the defaults; add a version only when one is needed. The fixed names (`weekly-schedules-workspaces`, `weekly-schedules-prefs`, `weekly-schedules-encrypted`, `#data=e1.`) never change. **[C✓] How to change the format:** raise `FMT`, add `MIG[FMT-1]`, update `tests/fixtures/household.js` (the sample household, in the current format, using every optional field, plus an `ADDED[FMT]` entry that removes the new fields again so older sample files are compared with `householdAt(v)`), run `node tests/fixtures/make.mjs` (writes `tests/fixtures/v<FMT>/` with the app's own save functions and refuses to overwrite a folder) and add the new key list to `SHAPES` in `tests/app/compat.test.js`. **Sample files of every published version** (`tests/fixtures/v<N>/`: readable file, encrypted file, link — password in `household.js` —, browser store with two workspaces, settings) are **never edited or regenerated**; tests load each through the real screens and check the content. A **shape check** fails when the keys the app writes differ from the frozen list of the current version, so a format change without a new version number can't slip through.
- **R-DATA-09** **[U]** **Data from a newer version is refused, never half-read** (it only reaches an older app through a stale cached page or an old copy kept on disk): a file or link whose workspace version is above `FMT`, an encrypted file whose container `version` is above 1, a blob whose layout byte or compression flag is above 1, or a link prefix `e2.` and up gives the message *made with a newer version… Reload the page (or update your copy of the app)* — before the password is asked whenever the version is visible from outside — and changes nothing. **Browser memory written by a newer version** is neither loaded nor overwritten: at startup an alert explains it and the app starts with a default workspace; saving to browser memory (current or all, also when another tab wrote the newer data later) and *Load → Browser memory* are refused with an explanation; *Restart* checks again; saving to a file still works; *Clear memory* (with its confirmation) deletes it, after which saving works again. A first-time visitor opening a link gets the import dialog instead of adopting it, since browser memory is not empty.

## 11b. Security (threat assessment decisions)
Threat model: a static, client-only app (no server, accounts, network calls or third-party code); the data at stake is personal schedule information in the browser and in shared files/links. Decisions **[U]**:
- **R-SEC-01** **Content-Security-Policy** `<meta>` in the page: `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; connect-src 'none'; base-uri 'none'; form-action 'none'`. Even if an escaping bug let foreign code run, it could not contact other sites or load outside content. `'unsafe-inline'` is needed because everything is one file, so the policy does *not* stop an injected inline script by itself (a build step with hashed scripts could tighten it later). `frame-ancestors` (clickjacking) can't be set from a meta tag on GitHub Pages — accepted, low impact. **Any new resource type (fonts, images from URLs, workers, network calls) needs a deliberate CSP change; check the browser console for "Refused to…" messages after edits.**
- **R-SEC-02** **Escaping rule:** every piece of user-controlled text that goes into `innerHTML`/`insertAdjacentHTML` must pass through `esc()` (escapes `& < > " '`); prefer `textContent`/DOM properties. Imported colours are reduced to `#rrggbb` (`normHex`), names/titles capped at 200 and descriptions at 5,000 characters.
- **R-SEC-04** **Nothing leaves the device** (except files the user downloads: the JSON export and the statistics CSV, the only two `Blob`s): no `eval`, `new Function`, `document.write`, `fetch`/XHR/WebSocket/`sendBeacon`/`window.open`, no cookies, no third-party code; only the two documented `localStorage` keys are written.
- **R-SEC-03** **Import limits** (`LIM`, files and links only, never the browser store): 100 schedules, 500 people, 100 activity types, 5,000 events, 100 rhythms, 2,000 phases, 200 repetitions per event/phase; links additionally capped at 2 MB when decompressed. Exceeding a limit rejects the import with a clear message.
- **Link/file privacy:** links are always encrypted with a user-visible password, exported files too unless the user deliberately picks *Unencrypted* after a warning (see §10); the data sits in the `#` fragment. Limits that remain: whoever has link *and* password can read and forward it (no revocation/expiry without a server), a short or reused password can be guessed offline (hence the generator and the 20-character minimum), the link length hints at the amount of data, imported/saved data is plaintext again in browser memory and in memory-only exports such as an anonymised copy's source, and a tampered hosted page could capture typed passwords (repo/hosting protection).
- **R-SEC-05** **Hosting advice (not code):** on GitHub Pages all sites of one account share the origin `name.github.io`, so other pages there can read this app's saved data → prefer a custom domain or a dedicated account/organisation; protect the repository (two-factor sign-in, protected main branch, HTTPS enforced) because whoever can change the code can read users' local data. Browser storage is unencrypted (shared computers: use Clear memory; keep JSON backups).
- **Automated checks:** see §14 (`npm test`, `npm run test:e2e`). Re-run them after every change that touches HTML building, import or links.

## 14. Testing
**Run:** `npm install`, then `npm test` (Vitest 5 + jsdom, 1,228 tests, ~65 s), `npx playwright install` once (on WSL or a fresh Linux machine also `sudo npx playwright install-deps` once, otherwise Chromium can't start and *every* e2e test fails with `error while loading shared libraries`), then `npm run test:e2e` (Playwright, 172 tests, ~4 min; `openApp` in `tests/e2e/helpers.js` starts with both Fit boxes off for predictable geometry, `defaults: true` gives the real defaults; Chromium + a Pixel 5 profile for `touch.spec.js`; `ALL_BROWSERS=1` adds Firefox/WebKit, which have not been run yet), `npm run lint`. CI: `.github/workflows/tests.yml` (lint + fast tests + Chromium on every push, all browsers nightly).

**Layout**
- `tests/unit/` pure logic through the page's own functions (time, colours, visibility rules, validation, encryption, translations).
- `tests/app/` behaviour of the screens in jsdom: grid, events, repetitions, choosers, schedules/people, phases, workspaces, import/transfer, share, print/agenda, touch, UI.
- `tests/security/` CSP, escaping with hostile data on every screen, no risky APIs, no network, limits.
- `tests/e2e/` real browser: geometry (sticky, scrollbars, lips flush, zoom, fit), real mouse/keyboard interaction, phone touch, downloads/links/clipboard in two browser profiles, print to PDF, CSP enforcement, performance budgets, accessibility ratchet. `tests/e2e/serve.js` serves `index.html` on http://localhost:4173 (a secure context).
- `tests/helpers/app.js` jsdom harness: `openApp`, `setData`, `dragFrom`, `createDrag`, `fillDialog`, fake column geometry (`.day` n spans x 100n..100n+100, top 0), stubbed dialogs/crypto/downloads/clipboard/print.
- `tests/fixtures/` frozen sample files of every published data format (`v<N>/`), the sample household (`household.js`) and the generator (`make.mjs`), see R-DATA-08; read by `tests/app/compat.test.js`.
- `tests/requirements.test.js` traceability + description quality.

**Rules**
- Every test group is named `R-AREA-nn <what is checked>` after a requirement in this file; individual test names must say what is expected (≥ 25 characters, no duplicates, no skip/only/todo). The console output is the documentation. New requirement → new ID here → tests.
- jsdom has no pointer-event handler attributes (`el.onpointerdown = f` is just a property), so jsdom tests call the handlers directly (`el.onpointerdown(fakeEvent)`, `col.onpointermove(...)`); document-level listeners do receive dispatched events. jsdom has no layout, so anything about sticky/scroll/real drag/print belongs in `tests/e2e`.
- Playwright's `page.evaluate` is exempt from the page's CSP (eval works there); to test `eval` blocking, inject an inline script that runs later (see `security.spec.js`). Headless Chromium never shows the real `beforeunload` dialog, so those tests fire the event and check `defaultPrevented`. Playwright hides scrollbars by default; the config keeps real ones (`ignoreDefaultArgs`).

**Bugs found by the suite and fixed (keep the tests)**
1. Saving with one workspace left did not drop deleted workspaces from browser memory (they came back after reload): `saveTo` now saves "all" when only one workspace exists.
2. Right-click on an event, phase or lip also started a drag/opened the edit dialog, hiding the copy menu: the pointer-down handlers ignore non-primary buttons.
3. A touch long-press drag of an existing event stalled after the first move (the redraw removes the touched element, so touch events no longer reached `document` and the browser started scrolling): `press()` captures the pointer on `body` and attaches a non-passive `touchmove` blocker to the touched element itself. Verified in Chromium touch emulation only — **try it on a real phone (Android Chrome and iOS Safari).**
4. Lip text colour is chosen by WCAG relative luminance (`lum`/`ink`), not HSL lightness (white text on yellow was ~1.6:1).
5. Clicking an existing phase in Phases mode did nothing when the workspace had people: `openDlg` read `involved` of the phase (phases have none) and crashed. Found by the user; the earlier tests used data without people.
6. A resize handle could be covered by an overlapping box: always for phases listed after the one being resized, and for events when the lower event's schedule opacity was below 100 % (opacity makes the box its own layer). Handles are now separate elements in the day column above every box (`.rz`, `box._rz`, `z-index:6`). Found by the user.

**Known issues (not fixed)**
- Accessibility (`tests/e2e/a11y.spec.js` is a ratchet: fails on new kinds or more elements; lower the numbers as you fix): unlabeled inputs (`label`: sidebar rename fields; the event dialog is now clean and its ratchet is `{}`), hour labels with low contrast (19), `#wrap` not keyboard-focusable (`scrollable-region-focusable`), selected Events/Phases button contrast in dark mode.
- Performance (this sandbox): drawing 1,000 events ≈ 0.6 s, 2,000 ≈ 1.6 s, 5,000 ≈ 3.9 s (superlinear). 5,000 events necessarily overlap heavily (≤ 96 non-overlapping per day), so the import limit is a safety cap, not a promise of smooth use. Budgets in `perf.spec.js`: 5,000 events < 15 s, 1,000 events < 3 s.
- Minor: a decompression bomb is reported as "not a valid save file" (the `'big'` branch of `askPassword` is never reached because `inflate` throws `'too big'`); a link with an empty payload asks for a password before saying it is invalid.
